### B-004 · ARRIVED phase doesn't stop the streamer — stale position stream + unfiled PIREPs

- **Status:** 🟥 OPEN
- **Date:** 2026-05-12
- **Tester:** Thomas K (export from flight-gsg-24.json, CFG 1641 EDDM→EDDL Session 703)
- **Build:** v0.7.15 client (tester pilot is not yet on v0.7.16/v0.7.17)

**Symptom:**
- Pilot lands at EDDL at 13:22 UTC (touchdown captured)
- FSM transitions phase → ARRIVED ✅
- **But:** position updates keep coming in for another 1:29h, last heartbeat at 14:51 UTC
- Last position: 44.486°N, 6.570°E (southern France/Alps, ~750 km from the destination airport EDDL)
- Aircraft state: FL318, 472 kt GS, engines on, on_ground=false
- PIREP `QG1mAQon8V0an1jy` is missing entirely from the PIREP list → was never filed

**Likely sequence of events:**
1. Pilot lands at EDDL
2. For some reason doesn't click "End Flight" (forgot, app bug, or validation failed)
3. Starts a different flight in the sim (sim restart, new aircraft, something far away from EDDL)
4. The streamer in AeroACARS keeps running — sends positions with the old `pirep_id` QG1mAQon8V0an1jy
5. The server-side recorder accepts them via `pirep_id` join (v0.7.15 F4 feature) → reports a 1:29h position series with the aircraft 750 km away from the arrival airport

**Code root cause:**
- `flight.stop.store(true)` only happens in `flight_end` / `flight_end_manual` / `flight_cancel`
- FSM phase ARRIVED does **not** automatically stop the streamer
- The pilot must explicitly click "End Flight" — if they forget, everything keeps running

**Fix options:**
1. **Auto-stop on ARRIVED + prolonged silence:** if phase is ARRIVED + `on_ground=true && groundspeed<1 && engines=0` for ≥5 minutes → automatically stop the streamer with an activity-log warning "Flight not manually ended — position stream stops after 5 min stationary"
2. **Sanity check "phase ARRIVED but aircraft flying":** if `phase == ARRIVED && !on_ground && groundspeed > 100` → activity-log error + streamer stop ("Aircraft flying after landing — ending old flight, start a new flight")
3. **Pilot reminder:** if phase ARRIVED is reached and no "End Flight" action has happened after 2 minutes → prominent UI banner

**Where:**
- `client/src-tauri/src/lib.rs` FSM tick loop and/or position-streamer loop
- Also server-side in the recorder: the position stream should stop accepting `pirep_id` joins after `phase_changed→ARRIVED`

**Priority:** **high** — corrupts PIREP/recorder data (aircraft jumps from the destination airport to southern France in the position track), and the pilot loses their PIREP filing

**Target release:** v0.7.17 (bundle patch)

### B-010 · FSM phases not suitable for GA/Cessna (spurious Cruise→Descent/Approach)

- **Status:** 🟥 OPEN
- **Date:** 2026-05-12
- **Source:** GSG 105 LDDU→LDSP, aircraft total weight 1,000 kg (Cessna class), X-Plane 12

**Symptom (from flight-APMVJmeQJWmP3MXk JSONL):**

```
17:26:53  Climb->Descent    AGL 2692 ft  (aircraft climbing!)
17:27:13  Descent->Approach AGL 2802 ft  (AGL ROSE between 2 phases!)
17:32:20  Approach->Climb   AGL 1877 ft  (Go-around)
17:49:35  Climb->Descent    AGL 3575 ft
17:49:41  Descent->Approach AGL 3540 ft  (6 seconds in Descent!)
```

AGL INCREASED between Climb->Descent and Descent->Approach — physically impossible for a real descent. The FSM misclassified this.

**Root cause** in `client/src-tauri/src/lib.rs:13223`:

```rust
let low_altitude_descent = vs < -100 && agl_ft < 3000.0 && lost_from_peak > 500.0;
```

The thresholds are calibrated for **airline operations**:
- AGL < 3000 ft: normal for a Cessna in the pattern (pattern altitude ~1500 ft AGL!)
- `lost_from_peak > 500`: for small VFR patterns (climbing to 3000, brief dip to 2500 for sightseeing), this fires as a phantom descent

→ The FSM oscillates between Climb/Descent/Approach on normal GA patterns (pattern work, sightseeing tour, short hops).

**Fix options:**

1. **Aircraft-type-aware FSM:** if total weight < 5000 kg (light GA) → longer dwell times + more generous VS thresholds
2. **Pattern detection:** if AGL never exceeds 5000 ft + sustained < 3000 → a dedicated pattern FSM that doesn't oscillate as much between Climb/Approach
3. **Hysteresis:** phase changes require a 30-60 s sustained condition, not a single tick
4. **Higher lost_from_peak:** > 1000 ft instead of 500 ft, so small dips don't trigger it

**Priority:** **high** — all GA pilots in the VA are potentially affected, FSM phases feed the activity log + PIREP custom fields + approach-stability score

**Target release:** v0.7.17 (bundle patch)

**Update 2026-05-12 (12) — NO sample spikes, REAL sim physics:**

Analysis of the `touchdown_window` samples shows:
```
Frame    VS     G      OnGround   Gear-Force-N
[126]  -116   0.98    false      0          (before touchdown)
[127]  -103   1.75    TRUE       (edge)
[128]   -46   2.30    true       13.682     ← strut-compression peak
[129]   +18   1.61    true       (rebound)
[130]   +18   1.61    true
[131]   +47   1.05    true       (settled)
```

The 2.30 G is **genuine sim physics** — strut compression on a 1,000 kg Cessna:
- F = 13.682 N
- a = F/m = 13.68 m/s² = 1.39 G in addition to gravity
- Plus 1 G = 2.39 G total — matches exactly

→ **X-Plane simulates the Cessna strut too stiffly**: for a -116 fpm landing, a real strut sensor would show 1.3-1.5 G, not 2.3. But that's sim-engine behavior, not an AeroACARS bug.

**Real root cause:** our classification logic `worse_of(by_vs, by_g)` is wrong relative to what the pilot actually perceives:
- The pilot feels V/S (= what they notice at touchdown)
- The pilot does NOT feel the strut-compression G (too short, too high-frequency)
- Currently: VS says Smooth (100), G says Severe (0), `worse_of` → Severe
- Frustration: "My -116 fpm butter landing is scored as Severe"

**Correct logic for v0.7.17:**

V/S leads, G is an upward modifier (can amplify a severe impact), but can never by itself lead to Severe when V/S is smooth.

Proposal:
```rust
let cat = match (by_vs, by_g) {
    (Smooth, Smooth|Acceptable|Firm) => Smooth,
    (Smooth, Hard|Severe) => Acceptable,  // strut anomaly, but pilot flew it well
    (Acceptable, Hard|Severe) => Firm,
    (Firm, Severe) => Hard,
    // Hard/Severe VS dominates
    (vs_cat, _) if vs_cat in (Hard, Severe) => max(by_vs, by_g),
    _ => by_vs,  // otherwise V/S leads
};
```

**Result:** a butter landing gets Smooth even if the sim strut spikes. Genuine hard landings (Vs < -600 fpm) continue to be classified correctly.

**Where:** `client/src-tauri/crates/landing-scoring/src/lib.rs:332-360` (classify function)

**Priority:** **critical** — a directly visible fairness issue

**Update 2026-05-12 (11) — X-Plane has the same bug, not just MSFS total-G:**

Tester finding GSG 105: touchdown VS -116 fpm (butter smooth), but `peak_g_post_500ms = 2.30 G`. Sim = X-Plane 12, and we already read `gforce_normal` (the vertical component). **Still 2.30 G in one of the 324 post-edge samples** — physically impossible for a 1,000 kg Cessna at a -116 fpm impact.

**So there are two separate G-force issues:**

a) **MSFS reads total G instead of vertical G** (original B-009)
b) **G-force sample spikes are counted as the peak** (NEW — sim-agnostic, affects both X-Plane and MSFS)

**Root cause (b):**

The sample stream has numerical spikes (strut-compression spring model, frame stuttering, etc.). We take `max()` over an 800ms window → a single 2.30G sample determines the score. Classifier: `worse_of(by_vs, by_g)` → VS says Smooth, G says Severe → **Severe wins even though the landing was butter smooth**.

**Fix (b):**

Instead of `max()`, use a more robust statistic:
- **Median** of the post-edge G samples
- OR **95th percentile** (absorbs 5% spikes)
- OR **rolling average** over 100ms sub-windows, then take the max of those
