## Block A — SimBrief Direct (v0.7.9 + v0.7.10)

### A1. Pre-Flight Preview (v0.7.10)

**Setup**: phpVMS bids prepared with a SimBrief link (at least 1 bid). Pilot Client shows **no** active flight.

1. Open the Bids tab
2. Click "Refresh"
3. Expected:
   - **Green banner**: `✓ Fresh SimBrief values loaded (N bid · direct from simbrief.com)`
   - Every bid card shows fresh SimBrief values (fuel, route, pax, wind) — these come directly from simbrief.com, **not** from the phpVMS pointer cache.

**Pass criterion**:
- Banner is **green** (not blue, not red)
- Values differ from what the phpVMS API returns directly (= more current than the pointer cache)
- For a bid WITHOUT a SimBrief link: banner shows `N of M bids could be refreshed`, others remain unchanged

### A2. Callsign soft warning (v0.7.9)

**Setup**: Configure SimBrief with a personal callsign (e.g. `4PY`), airline ICAO `EWG`. Record a phpVMS bid with operator code `EWL` (e.g. `EWL9725`). DEP/ARR in SimBrief = DEP/ARR of the bid.

1. Start the flight (IFR departure), then click "Refresh OFP" in the cockpit tab
2. Expected:
   - OFP **loads** (was a hard block in v0.7.7)
   - **Yellow warning notice** with concrete values:
     `OFP callsign is EWG4PY, your active flight uses EWL9725 / 9725 — DEP/ARR match, OFP was loaded`

**Pass criterion**:
- Refresh button shows **yellow**, not red (no hard block)
- OFP data is actually fresh (fuel/route/wind)
- X button on the warning notice dismisses it, reappears on the next refresh

### A3. DEP/ARR mismatch remains a hard block

**Setup**: SimBrief with DEP `EDDF`, bid with DEP `LOWG`.

1. Click "Refresh OFP"
2. Expected: **Red notice** with concrete DEP/ARR/callsign values. OFP is **not** loaded.

**Pass criterion**: DEP or ARR mismatch is a hard block (no soft warning).

## Known limitations

1. **Pre-v0.5.39 records** (very old) have no `vs_at_edge_fpm` in the payload. These fall back to the stored `vs_fpm` value — at that time this was NOT the SimVar value but the primary cascade output, so the display for these records is correct.

2. **Backfill in the DB** was **not** performed. The stored `landing_rate_fpm` column in the phpVMS database remains at the SimVar value for old records (-407 for DAL804). However, the VPS webapp recalculates for display from the buffer payload (-364) — i.e. **the display is correct, the DB value possibly is not**.

   → If a VA owner views phpVMS directly via SQL/export: values may differ from the UI. A solution would be a one-time backfill script. **Decision**: leave as-is for QS, evaluate later.
