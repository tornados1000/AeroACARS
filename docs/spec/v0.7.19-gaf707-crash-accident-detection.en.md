# v0.7.19 GAF-707 Crash / Accident Detection — Spec

**Status:** PROPOSAL — ready for implementation after v0.7.18-QA  
**Date:** 2026-05-13  
**Source:** GAF 707 incident from 2026-05-13, Pilot 15, JSON dump `C:\Users\kantt\Downloads\flight-gsg-15 (1).json`  
**Goal:** Stop treating real crashes as a normal "Severe Landing" — instead detect them as an Accident, make them visible, and cleanly separate them on the filing side.

## Summary

GAF 707 is not a telemetry reset and not a normal hard landing. The flight shows a real impact sequence:

| Signal | Value GAF 707 | Assessment |
|---|---:|---|
| `vs_at_edge_fpm` | approx. `-2249.9 fpm` | beyond Severe-Landing |
| `peak_g_load` | `4.41 G` | structural impact |
| `sideslip_deg` | `-115.6 deg` | uncontrolled contact |
| `landing_wing_strike_severity_pct` | `111.5%` | wing strike likely |
| `approach_stall_warning_count` | `5` | stall on final approach |
| `runway_match_icao` | `null` | no runway assigned |
| `rollout_distance_m` | `205.8 m` | not a normal airliner rollout |
| Score today | `0` | correctly low, but wrong semantics |

Today this only produces `score=0 / severe`. That is technically too little. The UI, webapp, MQTT, and PIREP must clearly state: **Crash / Accident detected**.

The VPS/webapp must be able to do this too — not just new client versions. Old history records like GAF 707 already contain enough payload fields for a retroactive classification.

## Problem

v0.7.18 B-013 guards against sim position resets:

- Null island (`lat/lon ~= 0/0`)
- Altitude jump > 10,000 ft
- Position jump > 10 nmi per tick

That resolves GAF 152, but not GAF 707. GAF 707 has no broken coordinates. The time series shows a physically consistent but catastrophic descent all the way to the ground:

| Time relative to TD | Altitude | GS | V/S |
|---:|---:|---:|---:|
| -89 s | 26,039 ft | 157 kt | -15,903 fpm |
| -66 s | 14,064 ft | 306 kt | -43,539 fpm |
| -8.8 s | 2,328 ft | 118 kt | -8,302 fpm |
| -1.1 s | 731 ft | 69 kt | -2,688 fpm |
| -0.1 s | 699 ft | 65 kt | -2,224 fpm |
| +0.4 s | 682 ft | 55 kt | -2,136 fpm |
| +3.8 s | 682 ft | 43 kt | -103 fpm |

This is not sample garbage — it's a crash/impact. B-013 must not filter this out.

## Key Decisions

### 1. Accident is not "an even worse landing score"

An Accident must not appear as a normal landing with score 0. Score 0 stays correct, but the category must be named differently:

- `severe_landing`: hard/structurally relevant landing, but still interpretable as a landing.
- `accident`: crash, loss of control, off-runway impact, or sim crash event.

UI text: **"Crash detected"**, not just **"Hard Landing"**.

The numerical score from the `landing-scoring` crate is **not** recalculated by accident detection. GAF 707 already gets score 0 today, because `vs_at_edge_fpm ~= -2250` and `peak_g_load = 4.41` are below every landing threshold. Accident is orthogonal to score calculation:

- Score remains numerically as before.
- Accident overrides the primary label / the classification.
- Accident prevents `clean_ifr` filing.
- The score tiles remain visible for forensics.

### 2. A simulator-neutral heuristic is mandatory, sim events are a bonus

According to the official SDK docs, MSFS/SimConnect has system events:

- `Crashed`: user aircraft crashed
- `CrashReset`: crash cut-scene completed

Reference: `SimConnect_SubscribeToSystemEvent`  
https://docs.flightsimulator.com/html/Programming_Tools/SimConnect/API_Reference/Events_And_Data/SimConnect_SubscribeToSystemEvent.htm

When MSFS delivers `Crashed`, that is a hard accident trigger. But this is only a bonus signal for MSFS. The actual accident detection must work **for all simulators**:

- MSFS
- X-Plane
- future sims/adapters

That's why the shared telemetry heuristic is not a second-class fallback, but the central path. Sim-specific events may only add extra confidence.

### 3. X-Plane is first-class

X-Plane must not be treated worse than MSFS. The X-Plane path uses the same accident heuristic based on:

- `vertical_speed_fpm`
- `g_force`
- `gear_normal_force_n` for the touchdown edge
- `velocity_body_x_fps` / `velocity_body_z_fps` for sideslip
- `stall_warning`
- `on_ground`
- Runway/airport resolution from v0.7.18

For X-Plane, this iteration does not assume a hard crash DataRef. If a stable crash/damage DataRef is verified later, it can be added as an additional signal (`crash_source = "xplane_crash_dataref"`). v0.7.19 must not depend on that, however.

### 4. Filing remains possible, but not as Clean IFR

A detected accident must not silently pass through as a clean IFR ACARS PIREP. The pilot gets a clear choice:

1. **File as accident/review**  
   PIREP is filed with score 0, accident marker, and notes. Afterward the flight must be cleanly ended: aircraft free, bid deleted/reservation gone, local active flight gone.
2. **Discard flight & cleanup**  
   Existing v0.7.18 orphan/cleanup path: cancel PIREP, release aircraft, delete bid, clean up local queue/state.
3. **Back**  
   Nothing happens, active flight remains.

For IFR, Accident is always at least `manual_review`, never `clean_ifr`. For VFR, filing remains possible, but is likewise visibly marked as an accident.

### 5. In uncertain cases, the client asks the pilot

Not every red marker automatically means a crash. There are hard landings, off-airport emergency landings, scenario flights, and simulator quirks. Therefore:

- `Confirmed` + sim event (`MSFS Crashed`) -> Accident pre-selected, pilot can still choose "No, treat as hard landing" if the sim triggered incorrectly.
- `Confirmed` from heuristic only -> dialog asks: **"Was this a crash?"**
- `Suspected` -> only a warning + question, no automatic accident filing.

The pilot may correct the result, but the correction is made visible in notes/audit:

```text
AeroACARS suspected accident, pilot overrode to hard landing.
Reasons: V/S -1050 fpm, no runway match, sideslip 38 deg.
```

### 6. CrashReset does not clear the active accident latch

`CrashReset` is a simulator UI/recovery event, not proof that the accident has been resolved from a business standpoint. If MSFS sends `CrashReset` after a crash dialog, the active flight must not lose its accident status.

Rule:

- The adapter may reset its raw `crashed` flag after `CrashReset` for new snapshots.
- `FlightStats.accident_detected`, however, stays latched until **flight end**, **cleanup/cancel**, or a **new flight start**.
- The accident dialog must still appear even if the pilot first clicks "Reset/Acknowledge" in the simulator and only afterward wants to file/cancel in AeroACARS.

### 7. Multi-touchdown aggregation: worst case wins

A PIREP can have multiple touchdowns: bounce, touch-and-go, training, intermediate landing, final touchdown. For the PIREP status:

```text
PIREP accident status = max severity across all touchdowns of this PIREP
```

Severity order:

```text
Confirmed Accident > Suspected Accident > Severe Landing > Hard Landing > normal/no accident
```

If multiple touchdowns have the same accident severity, the one with the highest absolute `vs_at_edge_fpm` wins. `accident_kind` and `accident_reasons` in the PIREP come from the worst-case touchdown. The webapp history must use the same aggregation, otherwise the client and VPS diverge on touch-and-go flights.

## Detection

### Additional trigger: MSFS `Crashed`

In the MSFS adapter:

```rust
const CRASHED_EVENT_ID: u32 = 302;
const CRASH_RESET_EVENT_ID: u32 = 303;

SimConnect_SubscribeToSystemEvent(handle, CRASHED_EVENT_ID, "Crashed");
SimConnect_SubscribeToSystemEvent(handle, CRASH_RESET_EVENT_ID, "CrashReset");
```

Dispatch:

```rust
if event_id == CRASHED_EVENT_ID {
    shared.crashed.store(true, Ordering::Relaxed);
}
if event_id == CRASH_RESET_EVENT_ID {
    shared.crash_reset_seen.store(true, Ordering::Relaxed);
}
```

Snapshot mapping:

```rust
snap.crashed = shared.crashed.load(Ordering::Relaxed);
snap.crash_source = if snap.crashed {
    Some("msfs_crashed_event".into())
} else {
    None
};
```

Acceptance:

- If `snap.crashed == true` during an active flight: `accident_detected=true`.
- `CrashReset` must not make the display disappear immediately. The active flight must retain the accident state.

### Classifier trigger points

There are two paths that can set `accident_detected=true`. They run at different points in time and must not be mixed:

| Path | Trigger | Latency | Data basis |
|---|---|---|---|
| Sim event path | `snap.crashed` flips `false -> true` while a flight is active | immediate, possibly before ground contact | Simulator event |
| Heuristic path | Touchdown edge in the 50 Hz sampler | at touchdown / LandingRecord build | `vs_at_edge_fpm`, `peak_g_load`, sideslip, runway, etc. |

#### Sim event path

As soon as `snap.crashed` flips from `false` to `true` and `active_flight` exists:

```rust
stats.accident_detected = true;
stats.accident_at = Some(now);
stats.accident_kind = Some("sim_crash".into());
stats.accident_confidence = Some("high".into());
stats.accident_reasons.push("simulator_crashed_event".into());
```

This path does not wait for a touchdown edge. That matters because a simulator crash event can already occur mid-air or in the crash dialog.

#### Heuristic path

`classify_accident(stats, analysis)` is **not** run on every 50 Hz loop tick. The call happens exactly when the touchdown edge is processed:

- in the same tick as `build_landing_record`, or
- directly after the landing analysis (`vs_at_edge_fpm`, `peak_g_load`, `runway_match_*`) has been materialized.

The result is stored in `FlightStats` and then reused for the client tab, flight-end dialog, MQTT, LandingRecord, and PIREP.

#### Overlap

Both paths may overlap:

- If the sim event fires first and the heuristic later delivers `Confirmed(Impact)`:
  - `accident_kind` stays `sim_crash` (the sim event is authoritative).
  - `accident_reasons` are extended with the heuristic reasons.
  - `accident_at` remains the first crash timestamp.
- If the heuristic fires first and a sim event comes later:
  - `accident_kind` may be upgraded to `sim_crash`.
  - `accident_at` remains the first accident timestamp.

Rationale: no flicker, no approach-stall false positives, no tick-by-tick reclassification.

### Shared trigger: impact heuristic

This path runs **identically for MSFS and X-Plane**. It must not assume any MSFS-only fields.

New pure function:

```rust
fn classify_accident(stats: &FlightStats, analysis: Option<&serde_json::Value>) -> AccidentDecision
```

Recommended result:

```rust
enum AccidentDecision {
    None,
    Suspected { kind: AccidentKind, reasons: Vec<String> },
    Confirmed { kind: AccidentKind, reasons: Vec<String> },
}

enum AccidentKind {
    SimCrash,
    Impact,
    OffAirportImpact,
}
```

#### Confirmed Accident

One hit is enough:

1. **Simulator crash event**
   - `snap.crashed == true`

2. **GAF-707 pattern: extreme impact**
   - `abs(vs_at_edge_fpm) >= 1500`
   - AND `peak_g_load >= 3.0`

3. **Off-airport impact**
   - `abs(vs_at_edge_fpm) >= 1000`
   - AND `runway_match_icao == None`
   - AND at least 2 additional red markers:
     - `peak_g_load >= 2.5`
     - `abs(sideslip_deg) >= 45`
     - `landing_wing_strike_severity_pct >= 100`
     - `approach_stall_warning_count >= 3`
     - `rollout_distance_m <= 300`

#### Suspected Accident

No hard confirm, but review banner:

- `abs(vs_at_edge_fpm) >= 1000`
- AND at least 2 additional markers:
  - `peak_g_load >= 2.1`
  - `abs(sideslip_deg) >= 30`
  - `landing_wing_strike_severity_pct >= 75`
  - `approach_stall_warning_count >= 1`
  - `runway_match_icao == None`

Suspected Accident is shown in the UI/webapp as a warning, but does not automatically block anything. Confirmed Accident switches the filing path to Accident/Review, but the pilot confirms or corrects the classification in the dialog.

### Anti-false-positive rules

These cases must **not** count as an accident:

| Case | Example | Expectation |
|---|---|---|
| Normal hard landing on runway | `-700 fpm`, `2.5 G`, runway match present, stable attitude | `severe_landing`, not Accident |
| Sim strut compression | `-116 fpm`, `2.3 G` | B-009 remains: acceptable/firm, not Accident |
| Soft off-airport emergency landing | `-300 fpm`, `1.4 G`, no runway match | Divert/off-airport, not Accident |
| B-013 reset sample | lat/lon 0/0 or altitude jump | Sample is discarded, no accident from it |
| MSFS pause/replay/reset | large gap `dt > 2s` | B-013 dt guard applies, no jump accident |

### Webapp History / VPS Reclassification

The webapp must not only show accident status when the new client sends `accident=true`. It must make a shared display decision for both old and new records:

1. If the payload has `accident=true`:
   - Adopt the client value.
   - Show `accident_kind`, `accident_confidence`, `accident_reasons`.

2. If the payload has `accident_classifier_version`:
   - Adopt the client decision.
   - Missing `accident` or `accident=false` means: the client classified and **no** accident was detected.
   - The webapp must not reclassify and override the client.

3. If the payload has neither `accident` nor `accident_classifier_version`:
   - The webapp/VPS recalculates using the same heuristic from the existing touchdown payload fields.
   - The result is marked as **"reclassified"**, not as an original client value.

4. If too few fields are present:
   - No accident banner.
   - Optionally, a small hint in debug/details: "Accident classification not possible, old payload incomplete."

This way historical flights like GAF 707 can appear correctly as an accident in the history, without the pilot having to fly it again with a new client.

Display example:

```text
Accident detected
Impact / High confidence / Reclassified from historical payload
```

History lists should not just show `score=0`, but a dedicated marker:

| View | Presentation |
|---|---|
| Touchdown detail | red accident banner with reasons |
| Landing history list | badge `Accident` instead of just score `0` |
| Pilot/VA history | filter/marker for accident, as far as the view shows scores/badges |

Important: reclassification on the web is **display and review logic**, not a retroactive phpVMS mutation. Old PIREPs are not automatically changed, no aircraft/bid actions for historical records.

### Webapp Multi-Touchdown Aggregation

History/PIREP views must not just take the last or first touchdown. For PIREP-level badges the same worst-case rule as in the client applies:

```text
Confirmed Accident > Suspected Accident > Severe Landing > Hard Landing > normal/no accident
```

Example:

- Touchdown 1: touch-and-go, `-120 fpm`, no accident
- Touchdown 2: crash, `-1800 fpm`, `3.2 G`
- History badge: `Accident`
- Detail reasons: from the second touchdown

For equal severity, the touchdown with the highest absolute `vs_at_edge_fpm` wins.

## Filing Rules

### IFR / Bid

| Accident state | Clean auto-file | Manual/review file | Cancel/cleanup |
|---|---:|---:|---:|
| none | allowed | allowed for normal recovery cases | allowed |
| suspected | not automatically clean; pilot must confirm | allowed with notes | allowed |
| confirmed | not clean | allowed as accident/review | allowed |

Confirmed Accident may never run through the new filing policy as `clean_ifr`.

### VFR / Free Flight

VFR stays relaxed, but not invisible:

- Accident may be filed.
- Notes/banner must be visible.
- No "Clean Landing" label.

## Accident Cleanup / phpVMS State

An accident must not leave an aircraft or a bid hanging on phpVMS. After every final pilot decision, it must be clear what server state results.

### Target state

| Pilot decision | PIREP | Aircraft | Bid |
|---|---|---|---|
| File accident/review | FILED / pending review with accident notes | free | deleted / reservation gone |
| Treat as hard landing | FILED with override notes | free | deleted / reservation gone |
| Discard flight & cleanup | CANCELLED | free | deleted / reservation gone |
| Back | unchanged IN_PROGRESS | stays reserved | stays reserved |

Important: "Aircraft free" is not optional. The GAF-707 pilot must not end up back at the VA admin's desk after an accident/cancel just because phpVMS still sees the aircraft as `in flight`.

### Operations

The client uses the same building blocks as v0.7.18 B-011:

1. **PIREP filed or cancelled**
   - Filing path: `file_pirep` / existing `flight_end` path.
   - Cleanup path: `cancel_pirep(pirep_id)`.
   - phpVMS/Disposable Basic releases the aircraft on cancel or completion. If phpVMS does not automatically release it after FILED, the spec implementation must treat that as a blocker.

2. **Bid drop**
   - After FILED or CANCELLED always attempt `delete_bid(bid_id, flight_id)`.
   - Order as in v0.7.18:
     - if `bid_id` present: `DELETE /api/user/bids` with `{ bid_id }`
     - on `400 | 404 | 422` and `flight_id` present: retry with `{ flight_id }`
     - if only `flight_id` present: directly `{ flight_id }`
     - if both missing: no bid drop possible, but write an activity log warning.

3. **Local cleanup**
   - `state.active_flight = None`
   - Delete persisted active flight
   - Empty the position outbox
   - `discard_queued_positions_for(pirep_id)`
   - `pirep_queue::remove(pirep_id)`

### Order for "File accident/review"

```text
Pilot confirms accident
  -> file_pirep with accident=true / score=0 / notes
  -> if FILED or QUEUED:
       - on QUEUED: NO cancel_pirep, no bid drop now; the queue must drop the bid later after successful filing
       - on FILED: delete_bid(bid_id, flight_id)
       - if delete_bid fails transiently: persist pending_bid_cleanup
       - local cleanup
  -> on HardFail:
       - active_flight remains
       - Dialog: "Filing failed. Discard & cleanup anyway?"
```

Rationale: on a transient error, no cancellation must occur, otherwise the same data-loss bug as B-014 would arise. If the accident PIREP is sitting in the queue, a queue success hook must catch up on the bid drop.

### Pending Bid Cleanup Queue

If `file_pirep` succeeded, but `delete_bid` afterward fails due to network/5xx/timeout, the pilot must not be left with a filed PIREP and a hanging bid. For this, v0.7.19 needs a small persistent cleanup queue:

```rust
struct PendingBidCleanup {
    pirep_id: String,
    bid_id: Option<u64>,
    flight_id: Option<String>,
    reason: String, // "accident_filed" | "hard_landing_override" | future
    created_at: DateTime<Utc>,
    last_attempt_at: Option<DateTime<Utc>>,
    attempts: u32,
}
```

Rules:

- After FILED + `delete_bid` transient fail: persist the entry.
- Background worker retries `delete_bid(bid_id, flight_id)`.
- On success: delete the entry and log activity/event.
- On permanent 4xx other than known fallback codes: make the entry visible, so the B-011 cleanup/details can display the state.
- `pending_bid_cleanup` must never trigger `cancel_pirep`. The PIREP is already filed; it's only about the reservation now.

### Order for "Discard flight & cleanup"

```text
Pilot confirms cleanup
  -> cancel_pirep(pirep_id)
  -> delete_bid(bid_id, flight_id)
  -> local cleanup
  -> Activity Log: "Accident discarded, PIREP cancelled, aircraft/bid released"
```

If `cancel_pirep` returns 404:

- The PIREP no longer exists server-side or was already cleaned up.
- UI asks as in v0.7.18: **"Remote PIREP not found, forget locally?"**
- On confirmation: local cleanup + still attempt `delete_bid`, if `bid_id`/`flight_id` are present.

### Queue Success Hook

If accident filing lands in `pirep_queue` due to network/5xx, the same cleanup must happen after a successful retry as for a direct FILED:

```text
pirep_queue worker filed accident PIREP successfully
  -> delete_bid(bid_id, flight_id)
  -> if delete_bid fails transiently: persist pending_bid_cleanup
  -> remove queue entry
  -> ensure local active flight is gone
  -> activity/log event
```

For this the queue must store enough metadata:

```rust
queued_pirep.bid_id: Option<u64>
queued_pirep.flight_id: Option<String>
queued_pirep.accident: bool
```

If the queue does not have these fields today: v0.7.19 must add them, or the accident path must not display as "done" on a transient filing error.

## Acceptance Criteria

- GAF 707 is classified as `accident=true`, `accident_kind=impact`, `confidence=high`.
- GAF 707 no longer appears only as a normal "Severe Landing".
- The MSFS `Crashed` event is subscribed to and latched as an accident in the active flight.
- MSFS `CrashReset` does not clear the active accident latch; the status stays until flight-end/cleanup/new flight start.
- The sim event path sets accident immediately; the heuristic path only runs at the touchdown edge, not per 50 Hz tick.
- `accident_at` is persisted in FlightStats, LandingRecord, MQTT/TouchdownPayload, and PIREP payload.
- `landing-scoring` remains unchanged; accident changes the primary label/filing policy, not the numerical score calculation.
- X-Plane detects hard impact crashes via the same heuristic, even without a sim-specific crash event.
- For heuristic cases the pilot is asked **"Was this a crash?"** and can confirm the accident or override it as a hard landing.
- v0.7.19+ payloads contain `accident_classifier_version`; the webapp uses this to distinguish "classifier ran, no accident" from "historical payload".
- For multi-touchdown PIREPs, the highest severity across all touchdowns wins.
- B-013 reset samples do not produce an accident.
- B-009 G-force mitigation remains intact: `-116 fpm / 2.30 G` does not become an accident.
- An IFR accident cannot file as `clean_ifr`.
- The pilot always has a conscious choice: file accident/review, cleanup, or back.
- After accident-FILED or accident-CANCELLED, the aircraft is free on phpVMS.
- After accident-FILED or accident-CANCELLED, the bid is deleted or the reservation removed.
- For queued accident filing, the bid drop is caught up after a successful queue retry.
- For FILED-ok/delete_bid-transient-fail, `pending_bid_cleanup` is persisted and retried later.
- Webapp and client show the same accident status.
- Webapp/VPS can reclassify historical touchdown payloads without an `accident` field.
- GAF 707 appears in the webapp history as `Accident`, not just as a score-0 landing.
- GAF 707 appears on the webapp **Landing Analysis** page as `Crash/Accident`, not as a normal `Hard Landing` / `Bone-Rattler` classification.
- GAF 707 appears in the AeroACARS client's **Landing** tab as `Crash/Accident`, not as a normal `Hard Landing` / `Bone-Rattler` classification.
- The control fixture from the same export remains `not accident`.
- Historical reclassification does not mutate old phpVMS PIREP states and does not trigger any aircraft/bid cleanup.
- All new fields are backwards-compatible (`serde(default)` / optional JSON).
