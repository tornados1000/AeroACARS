# v0.8.0 — Centralized Navdata + Runway Awareness

**Status:** PROPOSAL — ready for implementation after v0.7.21
**Date:** 2026-05-13
**Source:** MS713-QC-finding 2026-05-13 (HECA→OLBA, B738, X-Plane) + GSG-VA-owner wishlist
**Goal:** AeroACARS evaluates touchdowns against real Jeppesen/AIRAC data instead of against OurAirports (±10 m off). Webapp + pilot client display the touchdown graphically on a to-scale runway. Single source of truth is the VPS, all pilots are on the same data set. License-compliant via facts-only extraction.

## Summary

Today the touchdown is evaluated against runway data from the community CSV `ourairports-runways.csv`. For MS713 this showed a cross-track offset of `+2.4 m RIGHT` — but the photo, Google satellite image, and Navigraph cycle 2604 all say `~6.6 m LEFT`. That's a 9 m discrepancy **caused solely by incorrect threshold coordinates in OurAirports**.

v0.8.0 eliminates the problem structurally:

1. **VPS hosts central navdata** — the VA admin imports runway facts (lat/lon, heading, length, GS, TCH, displaced threshold) from his own licensed Navigraph source. Only extracted geographic facts land on the VPS, **no Navigraph/Jeppesen compilation** — license-compliant.
2. **Pilot client fetches the bid airports' runway data at flight start** from the VPS. Cached locally per PIREP. OurAirports remains only as an offline fallback.
3. **Seven data-driven features** are unlocked: precise off-centerline, correct runway-length utilization, touchdown-zone assessment, aim-point score, TCH compliance, displaced-threshold warning, correct wind-vs-runway vector.
4. **Graphical runway display** in the pilot client ("Landing" tab) and webapp (LandingAnalysis). To-scale runway with TDZ box, aim marker, pilot touchdown point, and compliance pills.

Out of scope for v0.8.0 (separate spec): glide-slope compliance on final, SID/STAR/approach compliance, approach-lights detection, approach-stability v3.

## Problem

### MS713 anchor (HECA → OLBA, 2026-05-13)

| Source | Threshold 17 Lat | Threshold 17 Lon | Cross-track offset MS713 |
|---|---|---|---|
| OurAirports (today) | 33.83820 | 35.48710 | **+2.4 m RIGHT** |
| Navigraph 2512 | 33.838364 | 35.486977 | **−6.6 m LEFT** |
| Aerosoft DFD 2604 | 33.838364 | 35.486978 | **−6.6 m LEFT** |
| Photo + Google sat | — | — | **clearly LEFT** |

OurAirports has the OLBA RWY 17 threshold ~11 m east of reality. The pilot client therefore incorrectly shows "right of centerline" even though photo/map/real Jeppesen data all say "left." Similar mismatches likely exist at dozens of GSG airports — OurAirports is community-crowdsourced, quality varies per entry.

### Structural cause

- **Data model:** the pilot client gets only ONE runway record from ONE source (OurAirports CSV in the binary). No update mechanism, no quality fallback, no sim/AIRAC sync.
- **Quality distribution:** OurAirports has heterogeneous quality — some airports good, some bad. No way for the VA to feed in corrections centrally.
- **Currently missing data:** TCH, displaced threshold, glide-slope angle, precise magnetic variation, approach lights — none of it in OurAirports. That makes entire classes of assessment impossible.

### Data already available at the VA admin

VA owner Thomas K has an active Navigraph subscription (FMS Data Manager, cycle 2604, source: Jeppesen). His Aerosoft Airbus DFD cycle sits under `E:\NAV_DATA\` as a plain-text format with all relevant fields. This data may **be read locally by him and converted into geographic facts** (no copyright issue with factual data). Distributing the Navigraph compilation to pilots is EULA-prohibited — distributing **extracted facts** in his own format is not.

## Key Decisions

### 1. VPS is single source of truth for navdata

All pilots pull their runway data from the VPS at flight start. No pilot client has a built-in AIRAC cycle. OurAirports stays in the binary, but ONLY as an offline fallback if the VPS is unreachable.

Rationale: one update suffices. The VA admin maintains it once per AIRAC cycle, all pilots are current. No pilot-side Navigraph subscription needed.

### 2. The VPS holds geographic facts, NOT a Navigraph compilation

VPS schema stores: `airport_icao`, `runway_designator`, `threshold_lat/lon`, `runway_length_ft`, `width_ft`, `magnetic_course`, `glideslope_angle`, `tch_ft`, `displaced_threshold_ft`. These are pure geographic facts. No Navigraph branding, no Jeppesen format, no procedures hierarchy. Own schema, own wire form.

Rationale: factual data is not copyrightable (Feist v. Rural, US Supreme Court 1991; analogously EU database law: §87b UrhG threshold of originality). The VA admin, as a licensed subscriber, interprets the compilation once and extracts the facts — distributing the facts is legal.

### 3. Admin upload only by the VA admin

The webapp gets an admin tab "Navdata." Admin uploads a DFD source (Aerosoft format as MVP, more sources later). Recorder parses locally on the VPS, writes extracted facts to `nav_runways`. Atomic replace (= either the whole cycle succeeds or a complete rollback). Nobody but the admin can upload — bearer-token auth.

Rationale: a single-admin workflow is simple. Multi-admin or pilot crowdsourcing comes at the earliest in v1.0.

### 4. Pilot client caches per PIREP, not globally

At flight start the pilot client fetches the 1–3 runway records for dep/arr/alt from the VPS. Cached in `ActiveFlight.navdata`. Cache lifetime = lifetime of the active flight (= until PIREP is filed). No local persistence file, no global cache.

Rationale: minimal network footprint (1–3 REST calls instead of a mega-sync), no stale-cache risk, no update-logic overhead. On connection loss the OurAirports fallback kicks in automatically.

### 5. License clause visible in code + UI

VPS webapp admin tab shows: "Data source: extracted from AIRAC 2604, licensed by <VA-admin-name> via Navigraph. Distribution only within GSG members." Pilot client activity log at flight start: "Navdata AIRAC 2604 loaded from aeroacars-live." This makes the source/license auditable for every run.

Rationale: defensive measure in case Navigraph asks. Even though facts-only is legally clean — transparency doesn't hurt.

### 6. Graphical runway display is mandatory, not "nice-to-have"

The entire data-driven assessment is only visible once the visualization exists. The pilot should see at a glance "TDZ box hit, aim 320 m past, 2 m left of CL." Webapp and pilot client show the SAME layout (with size adjustment) — consistency.

Rationale: explicitly requested by the VA owner. Without visualization the new data is just table values without pilot understanding.

### 7. OurAirports remains as fallback

When the VPS is unreachable (auth failure, network loss, server down, new airport not yet in the VPS cycle):
- Pilot client falls back to the built-in `ourairports-runways.csv`
- Activity log: "Navdata: OurAirports fallback active — VPS unreachable"
- Assessment pills in the LandingPanel show confidence level "LOW" with a hover hint "based on community data, ±10 m possible"

Rationale: the pilot can always fly, even offline. Quality degradation is visible, no standstill.

```sql

    id INTEGER PRIMARY KEY AUTOINCREMENT,
    cycle TEXT NOT NULL,                   -- "2604"
    revision INTEGER NOT NULL DEFAULT 1,
    valid_from TEXT NOT NULL,              -- "2026-04-16"
    valid_to TEXT NOT NULL,                -- "2026-05-14"
    source TEXT NOT NULL,                  -- "aerosoft_dfd"
    imported_at INTEGER NOT NULL,
    imported_by TEXT NOT NULL,             -- admin username
    airport_count INTEGER NOT NULL DEFAULT 0,
    runway_count INTEGER NOT NULL DEFAULT 0,
    is_active INTEGER NOT NULL DEFAULT 0   -- exactly one active row
);
CREATE UNIQUE INDEX idx_nav_cycles_active ON nav_cycles(is_active) WHERE is_active = 1;

CREATE TABLE nav_airports (
    icao TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    latitude REAL NOT NULL,
    longitude REAL NOT NULL,
    elevation_ft INTEGER,
    cycle_id INTEGER NOT NULL REFERENCES nav_cycles(id)
);

CREATE TABLE nav_runways (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    airport_icao TEXT NOT NULL,
    designator TEXT NOT NULL,              -- "17", "35", "09L", etc.
    magnetic_course REAL NOT NULL,         -- e.g. 172.0
    true_course REAL NOT NULL,             -- computed from threshold-to-end bearing
    length_ft INTEGER NOT NULL,
    width_ft INTEGER,
    surface_code TEXT,                     -- "ASP", "CON", "GRS", ...
    threshold_latitude REAL NOT NULL,
    threshold_longitude REAL NOT NULL,
    threshold_elevation_ft INTEGER,
    end_latitude REAL NOT NULL,            -- = threshold_lat of opposite RWY
    end_longitude REAL NOT NULL,
    displaced_threshold_ft INTEGER NOT NULL DEFAULT 0,
    has_ils INTEGER NOT NULL DEFAULT 0,
    ils_frequency_mhz REAL,
    glideslope_angle REAL NOT NULL DEFAULT 3.0,
    tch_ft INTEGER NOT NULL DEFAULT 50,
    ils_category INTEGER,                  -- 1/2/3, NULL for non-precision
    cycle_id INTEGER NOT NULL REFERENCES nav_cycles(id),
    UNIQUE(airport_icao, designator, cycle_id)
);
CREATE INDEX idx_nav_runways_airport ON nav_runways(airport_icao);
```

## Features in Detail

### F1: Off-centerline fix (MS713 anchor)

**What changes:**
- Today's cross-track calculation stays mathematically unchanged (`runway.rs:442–490`).
- Input data comes from `ActiveFlight.navdata.runways` instead of OurAirports.
- For the MS713 anchor: `+2.4 m RIGHT` → `−6.6 m LEFT` (= matches photo+map).

**Touch points:**
- `runway::match_runway()` gets a `RunwayDataSource` parameter (Navigraph vs OurAirports).
- `LandingRecord.centerline_distance_m` stays the same field; only the source changes.
- Activity log entry "Off-centerline X.X m (Navigraph)" or "... (OurAirports fallback)".

### F2: Correct runway-length utilization

**What changes:**
- `LandingRecord.runway_match.length_ft` comes from VPS data.
- The `sub_rollout` score in the `landing-scoring` crate uses the same input as today — but values change.
- Aircraft-aware thresholds from v0.7.17 N-002 remain.

**Example:** If OurAirports had OLBA RWY 17 at 10663 ft and Navigraph 10663 ft (= identical), nothing changes here. At other airports with OurAirports bugs, this can well be a 200 ft difference.

### F3: Touchdown-zone assessment (TDZ)

**Definition (ICAO Annex 14 / FAA 150/5340-1):**
- TDZ marking: first 900 m or first 1/3 of the runway (whichever is shorter).
- For runways < 1200 m: no TDZ marking defined, feature skips.

**What is computed:**
```
tdz_length_m = min(900, runway_length_m / 3)
tdz_start_distance_m = 0  (= threshold)
tdz_end_distance_m   = tdz_length_m

td_in_tdz = (touchdown_distance_from_threshold_m > 0)
         && (touchdown_distance_from_threshold_m <= tdz_end_distance_m)

td_third = which third of runway (1/2/3) the touchdown landed in
```

**Display pills:**
- `TDZ ✓ — 320 m past threshold (within 900 m marker)`
- `TDZ ✗ — 1430 m past threshold (long landing, third 2/3)`
- `TDZ — (runway < 1200 m, no TDZ standard)`

**Score impact:** no direct point deduction (at least in v0.8.0). Display + coaching tip only.

### F4: Aim-point score

**Definition (FAA AIM 8-9-1):**
- Standard aim point: 300 m past threshold (short runways) or 400 m (long runways ≥ 2400 m).
- The Aerosoft DFD doesn't contain an "aim point distance" field — we use the standard thresholds.

**What is computed:**
```
aim_point_distance_m = if runway_length_m >= 2400 { 400.0 } else { 300.0 }
aim_delta_m = td_distance_from_threshold_m - aim_point_distance_m
```

**Classification:**
- `|aim_delta| < 60 m` → **Perfect** (on/very close to the aim point)
- `aim_delta in [-150, -60]` → **Short of aim** (a bit early)
- `aim_delta in [60, 200]` → **Past aim** (a bit late, ok)
- `aim_delta in [200, 500]` → **Long landing** (warn)
- `aim_delta > 500` or `aim_delta < -150` → **Severe** (rollout-distance problem)

**Display pill:** `Aim @ 300 m — you at 320 m (+20 m, perfect ✓)`

### F5: TCH compliance (Threshold Crossing Height)

**Definition:**
- TCH = AGL when crossing the threshold line.
- Aerosoft DFD: `tch_ft` field per runway (typically 50 ft for ILS, can vary).

**What is computed:**
```
threshold_crossing_at = first sample where
    bearing_from_threshold to position is within ±90° of runway course
    AND distance_from_threshold > 0  (= over the threshold)

actual_tch_ft = altitude_agl_ft at threshold_crossing_at
expected_tch_ft = nav_runway.tch_ft

tch_delta_ft = actual_tch_ft - expected_tch_ft
```

**Classification:**
- `|delta| <= 5 ft` → **On TCH** (perfect)
- `delta in [-15, -5]` ft → **Slightly low** (just under threshold)
- `delta in [5, 20]` ft → **Slightly high** (too high, longer float phase expected)
- `delta > 20` ft → **High** (long-landing risk)
- `delta < -15` ft → **Below TCH** (dangerous — tail-strike risk, obstacle clearance)

**Display pill:** `TCH 49 ft — you at 47 ft (−2 ft, on profile ✓)`

**Data requirements:** we need the sample frame in which the aircraft crosses the threshold line. This is new logic in the pilot client; Spec §6.

### F6: Displaced-threshold warning

**When relevant:**
- `nav_runway.displaced_threshold_ft > 0` → the real threshold is X ft behind the painted line.
- A pilot who touches down before the real threshold lands on a "non-landing surface" (= red threshold marking).

**What is computed:**
```
if displaced_threshold_ft > 0
    && td_distance_from_threshold_m < (displaced_threshold_ft * 0.3048):
    flag = "TOUCHDOWN_BEFORE_DISPLACED_THRESHOLD"
```

**Display:**
- Activity log error: "Touchdown 80 m before displaced threshold (DDS 2690 ft / 820 m)"
- Webapp banner (red): "⚠ Touchdown in pre-threshold area"
- PIREP notes: audit entry

**Example:** OLBA RWY 35 has `displaced_threshold_ft: 2690` (= 820 m! a large displacement due to obstacles on the northern approach path). A pilot who touches down 800 m past threshold 35 actually lands on the DDS marking — illegal IRL.

### F7: Exact wind-vs-runway vector

**Today:** runway heading is computed from OurAirports + a rough approximation.
**With Navigraph:** `magnetic_course` (=170°) + `true_course` (=176.9°) directly from the DFD. Plus, the wind x/z vectors from the sim are already body-frame relative.

**What changes:**
- `LandingRecord.headwind_kt` / `crosswind_kt`: calculation uses the correct `true_course` as the runway axis.
- Subtle improvement, typically <0.5 kt — but costs nothing since the data is already there.

**Score impact:** marginal. Mainly important for statistics trending (= cleaner headwind/tailwind differential across all PIREPs).

## REST API Spec

### Pilot endpoints (read-only, auth via pilot token)

```
GET /api/navdata/airport/<ICAO>
  → 200 OK + NavAirport JSON (see wire format)
  → 404 Not Found if ICAO not in active cycle
  → 503 Service Unavailable if DB lock or cycle switch

GET /api/navdata/cycle
  → 200 OK { "cycle": "2604", "valid_to": "2026-05-14",
              "imported_at": "...", "airport_count": 8500, "runway_count": 17200 }

GET /api/navdata/airports?bbox=<min_lat>,<min_lon>,<max_lat>,<max_lon>
  → 200 OK [ { "icao": "OLBA", "name": "...", "lat": ..., "lon": ... }, ... ]
  → optional, for webapp map display
```

### Admin endpoints (auth via admin bearer token)

```
POST /api/admin/navdata/upload
  Content-Type: multipart/form-data
  Body:
    cycle:     "2604"
    source:    "aerosoft_dfd"
    archive:   <ZIP file with Airports.txt + cycle.json + optional proc/>
  →  202 Accepted { "job_id": "...", "expected_duration_secs": 30 }
     parse runs async, atomic replace after success

GET /api/admin/navdata/upload/<job_id>/status
  →  200 OK { "status": "parsing|done|failed",
              "progress_pct": 67,
              "airport_count": 8500,
              "runway_count": 17200,
              "error": null }

POST /api/admin/navdata/cycle/<cycle>/activate
  →  200 OK — activates the named cycle
     sets nav_cycles.is_active=1 for the chosen one, 0 for all others

GET /api/admin/navdata/cycles
  →  200 OK [ { "cycle": "2604", "imported_at": "...", "is_active": true }, ... ]
     list of all imported cycles for the UI

DELETE /api/admin/navdata/cycle/<cycle>
  →  204 No Content — deletes a cycle (not allowed if is_active=1)
```

### Auth

- Pilot token: existing pilot session token (from login).
- Admin token: separate bearer token in the recorder ENV (`AEROACARS_ADMIN_TOKEN`). A multi-admin-user system is out of scope for v0.8.0.

## Visual Design — Runway Diagram Component

### Layout

SVG-based, 4 horizontal layers:

```
Layer 1 (Top, Y=0-30):     Scale + annotations (distance markings every 500m)
Layer 2 (Y=30-80):         Runway box with markings
                           ┌─Threshold─┬─TDZ box─┬─Aim─┬─Middle section─┬─End─┐
                           │   ▏▎▎▏    │ #####   │  ↓  │              │ ▎▎▎ │
                           └─Centerline (dashed continuous)─────────┘
Layer 3 (Y=80-110):        Pilot track + TD point + rollout line
                           ●─────●●●●● (TD point large circle,
                                       rollout thin line to stop)
Layer 4 (Bottom, Y=110+):  Compliance pills horizontal
                           [TDZ ✓] [Aim ✓ +20m] [Off-CL -2.0m] [TCH 47/49ft] [Rollout 22%]
```

### Scaling behavior

- **To scale when possible:** pixels-per-meter from container width + runway length.
- **For small container width (< 600px):** vertical variant (runway top to bottom), same logic.
- **Runway width relative to runway length is NOT to scale:** we stretch the width by a factor of 3-5, otherwise the runway is a thin line (real 45 m wide over 3000 m long = 1.5% — visually illegible). The centerline offset is stretched by the same factor so ±2 m stays visible.

### Colors (webapp dark mode)

- Runway asphalt: `#3a3f47` (= dark gray)
- Threshold stripes: `#e6e9ee` (= whitish)
- Runway markings (designator "17"): `#e6e9ee` with stroke
- TDZ box: `#fde68a40` (transparent yellow, ICAO style)
- Aim-point arrow: `#fbbf24` (strong amber)
- Centerline (dashed): `#a3a3a3`
- TD point: tone-dependent (green/yellow/red depending on aim classification)
- Rollout line: same tone as TD point, semi-transparent
- Pre-threshold asphalt (when DDS > 0): `#7c2d1230` (dark red, marks forbidden zone)

Pilot client uses the same colors with slight adjustments for light mode.

### Hover tooltips

- **TDZ box:** "TDZ marking (ICAO Annex 14) — first 900 m or 1/3 of the runway. Intended touchdown area."
- **Aim point:** "Standard aim point — 300 m (short) or 400 m (long runway). Pilot should touch down here."
- **TD point:** "Touchdown @ 33.8336° / 35.4873° · 320 m past threshold · V/S −194 fpm · Peak G 2.52"
- **DDS zone:** "Displaced threshold — no landing permitted. 820 m from the physical runway start."

## Acceptance Criteria

- The VA admin can upload and activate a new AIRAC cycle via the webapp.
- Atomic replace: old cycles remain in the DB until manually deleted; the active cycle switches transactionally.
- The pilot client pulls navdata for dep/arr/alt from the VPS in parallel at flight start.
- On VPS outage / unknown airport: the OurAirports fallback kicks in transparently.
- The activity log shows the navdata source used (cycle + source) for every flight.
- MS713 replay yields `centerline_distance_m == -6.6 m` (was `+2.4 m`).
- LandingRecord contains the new fields `td_distance_from_threshold_m`, `td_in_tdz`, `td_third`, `aim_delta_m`, `tch_actual_ft`, `tch_expected_ft`, `pre_displaced_threshold`.
- TouchdownPayload (MQTT) provides the same fields with `skip_if_none` for backward compat.
- The pilot client LandingPanel shows the new runway diagram with TDZ box, aim marker, TD point, and compliance pills.
- The webapp LandingAnalysis shows the larger variant of the runway diagram.
- Long landings are made visually and coaching-tip visible.
- A DDS warning appears on touchdown in the pre-displaced area (red banner in pilot client + webapp).
- The seven data-driven features deliver stable values and are backward-compatible (old PIREPs without Navigraph data show the old values without a crash).
- API endpoints are pilot-token/admin-token authenticated; no anonymous reads/writes.
- DB schema migrations run idempotently on recorder restart.

## Open Decisions

- **Multi-admin auth:** v0.8.0 uses only a single `AEROACARS_ADMIN_TOKEN` from the ENV. Should v0.8.x support multiple admin accounts (per-user permissions, audit log of who uploaded what)?
- **Cycle-retention policy:** do we keep old cycles indefinitely, or auto-clean up after e.g. 12 months?
- **Pilot-client auto-refresh:** if the VPS activates a new cycle while a pilot is flying, should the pilot pull the new data mid-flight or keep the old cycle until end of flight?
- **DDS score impact:** should a touchdown before the DDS receive a score penalty or just a warning? VA-owner decision.
- **TDZ-threshold configuration:** ICAO 900m vs. FAA 3000ft (= 914m) — nearly identical, but are there VAs with other standards?
- **Procedures (proc/ files) in v0.8.x or v0.9.0?** Spec says out of scope. But if the parser is running anyway, we could already store the data (`nav_procedures` table) without consuming it — a later feature could build on it without re-import.
- **Which source format is mandatory?** v0.8.0 starts with Aerosoft DFD. If a VA admin has a different navdata format (e.g. only Little Navmap SQLite, Toliss format, FlyByWire DFD SQLite), we need multiple parsers. Proposal: for v0.8.0 only Aerosoft DFD, more parsers in v0.8.x if needed.
- **Visualization for very short / very long runways:** how does the runway diagram behave at extreme ratios (100m helipad, 5500m EDDF)? Stretch/compress or scale?
