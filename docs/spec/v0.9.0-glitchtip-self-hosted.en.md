# v0.9.0 — Self-hosted GlitchTip for AeroACARS

**Status:** PROPOSAL — ready for implementation after v0.8.4
**Date:** 2026-05-18
**Source:** Ops pain from the v0.8.3 bug-triage week (3 bug reports, each 1-3h of diagnosis via Discord screenshots)
**Goal:** Bug reports from pilots land automatically in a central triage inbox with stack trace + context, instead of staying trapped in Discord as screenshots. Self-hosted on live.kant.ovh (GDPR-compliant, no cloud lock-in, ~€3/month extra cost = $0).

## Mandatory Requirement (Telemetry Contract)

This spec is a **consumer** of [`v0.9.0-telemetry-contract.md`](v0.9.0-telemetry-contract.md). In case of conflict between this spec and the contract, the contract wins.

Concrete contracts this spec honors:
- **Tag sources** (Contract Section 1.1 + 1.2): Sentry tags `callsign`, `aircraft`, `dep`, `arr`, `simulator`, `phase` are read from canonical fields — NO independent calculation
- **Ownership** (Contract Section 3): The GlitchTip SDK writes NO AeroACARS telemetry fields, only Sentry's own event fields
- **Anonymization** (Contract Section 9 + Spec Section "LE5"): `pilot_id` as SHA256 hash, NO email/token/PIREP notes
- **Feature flag** (Contract Section 7): `error_reporting.enabled` (default `false`, opt-in via first-run banner)
- **Build order** (Contract Section 6): VPS setup (Step 0a) in parallel with Steps 0-3, SDK integration (Step 4) AFTER Steps 1-3 so tags use stable fields
- **Privacy gates** (Contract Section 9): DS1, DS4, DS5, DS6, DS7 are GlitchTip-specific and block release on fail
- **E2E tests** (Contract Section 8): G8 (GlitchTip offline) + G10 (opt-out) test robustness

## Summary

Today pilot bugs land **exclusively** in Discord screenshots. We guess the stack trace from the pilot's screenshot, ask for repro steps, search VPS logs by hand. A diagnosis takes 1-3h per report. As pilot count grows (12 → 30), that doesn't scale.

**GlitchTip** is an open-source clone of Sentry — equally API-compatible (= the Sentry SDK in all three codebases works 1:1), but drastically more lightweight (5 containers instead of 25, 500 MB RAM instead of 16 GB, simple updates). We self-host it on live.kant.ovh.

Concrete value after deployment:
- **Pilot crashes/gets an error** → 1 second later it's in our triage inbox with full context
- **Bug frequency visible** → we see which bugs affect many pilots, not just the loudest complainers
- **Release health tracking** → we immediately see when v0.9.0 performs worse than v0.8.4
- **Custom messages for non-crash events** → Adrian's "bounce not detected" class also gets reported automatically
- **Discord webhook** possible → new bug classes pop up automatically in the GSG Discord

Effort: ~3-4 h one-time (VPS setup, SDK integration in 3 codebases), then autonomous. Cost: $0/mo (self-hosted on existing VPS).

Out of scope: performance profiling (= Sentry premium feature), distributed tracing between services, mobile app SDK (we don't have one).

## Problem

### Anchor Cases from the Last Week

**Case 1 — Svenny PIREP spam (2026-05-17):**
- Symptom: ACARS log shows 47× red "PIREP file failed" messages
- How we found out: Discord screenshot from Svenny at 18:55
- How we found the cause: SSH into VPS → DB query for pirep_id → searched logs → read code → hypothesis → asked pilot back
- **Diagnosis time: ~2.5 h**
- With GlitchTip this would have been visible in 2 minutes: "Server { status: 400 }: PIREP is read-only — 47 events, 1 user, affects Bonanza TAPA→TRPG, stack points to lib.rs:8240"

**Case 2 — Adrian "bounce not detected" (2026-05-18):**
- Symptom: pilot sees "0 bounces" even though he had a bounce
- How we found out: Discord screenshot with an annotated arrow
- How we found the cause: VPS DB query on touchdowns → parsed JSON payload → discovered `bounce_max_agl_ft=14.05` → uncovered a code/spec conflict
- **Diagnosis time: ~1.5 h**
- With GlitchTip + custom forensics events: we would have seen "5 pilots in 7 days with forensic bounce but no scored bounce" after 5 similar touchdowns — we could have addressed the bug BEFORE Adrian's report

**Case 3 — Michel wetlease (2026-05-14):**
- Symptom: aircraft mismatch blocks flight start
- How we found out: Discord screenshot + free text
- How we found the cause: reading code + recorder DB query on aircraft_aliases
- **Diagnosis time: ~2 h**
- With GlitchTip + custom "FlightStartBlocked" events: we would have seen the most common mismatch pairs as an aggregate and proactively maintained aliases

**Overall finding:** 3 bug reports in one week = **~6 h of pure diagnosis time**. With GlitchTip that would have been ~30 min (= **-90% diagnosis effort**).

### Structural Cause

Today we have **no automatic path** for pilot errors back to us:

```
Pilot Error → ACARS log (local) → Pilot sees it
            ↓                    ↓
            (lost if the         (only if the pilot
             pilot doesn't       reports it — 90% do
             react)                NOT report)
```

Consequence: we only know the bugs that loud pilots report. We do **not** know:
- How often a bug occurs
- Which pilots are affected
- Which aircraft types / sims / OS versions are affected
- Whether a bug correlates with a specific version
- Whether a "fixed" bug is really fixed or still occurring

### Scaling Problem

Today: 12 pilots, ~3 reports/week = manageable via Discord.

At 30 pilots (growth target): ~8 reports/week × 2h = 16h/week bug triage. That's 1 workday per week **just for bug triage** — not scalable.

GlitchTip solves this structurally: reports arrive aggregated in a triage inbox, not as 8 separate Discord conversations.

## Key Decisions

### LE1 — GlitchTip instead of Sentry Cloud

| | Sentry Cloud | Sentry Self-Hosted | GlitchTip Self-Hosted (chosen) |
|---|---|---|---|
| License | Commercial | BSL → SSPL | MIT |
| Hobby price | $26/mo | $0 + server ops | $0 + server ops |
| Container count | n/a | ~25 | **5** |
| Min RAM | n/a | 16 GB | **512 MB** |
| Update effort | n/a | complex | `docker compose pull` |
| SDK compatibility | native | native | **1:1 Sentry SDK** |
| Migration path to Sentry later | trivial | trivial | **trivial** (SDK-compatible) |

**Rationale:** We get 95% of Sentry's features for $0 and 5% of the ops effort. Migrating to real Sentry later is a DSN change in the code — no code refactor.

### LE2 — Self-Hosted on live.kant.ovh

| | Cloud (GlitchTip.com) | Self-Hosted (chosen) |
|---|---|---|
| Setup | register DSN | docker-compose + Caddy + 30 min |
| Cost | $0-15/mo | $0 |
| GDPR | EU server available | full control, all data in EU |
| Privacy banner | pilot info needed | pilot info needed, easier to argue ("all data with us") |
| Event limits | 1k/mo free, then $ | unlimited |
| Maintenance | none | `docker compose pull` 1×/month |

**Rationale:** VPS has 3.4 GB RAM free. Hetzner datacenter is EU (GDPR-trivial). No vendor lock-in. Maintenance effort negligible for 5 containers.

### LE3 — Three SDK Integrations: Client (Rust+TS), Recorder (Node), Webapp (TS)

All three codebases get their own Sentry SDK + DSN env var. All send to the same GlitchTip project "aeroacars" with a different `release` tag:
- `aeroacars-client@0.9.0` (Rust + React)
- `aeroacars-recorder@0.9.0` (Node)
- `aeroacars-webapp@0.9.0` (React)

In the triage inbox you then see per issue which component it came from (= `release` tag).

**Rationale:** cross-component visibility. A bug in the client and a bug in the recorder appear in the same dashboard, aggregated by component.

### LE4 — OPT-IN, Default OFF

**Binding default:** `error_reporting.enabled = false`. On a fresh install + on upgrade from v0.8.4, the flag is OFF. NO Sentry SDK is initialized, not a single event is sent, unless the pilot actively opts in.

The first app start after the v0.9.0 update shows a one-time notice:

> "AeroACARS would like to send anonymized error and crash reports to our VPS so we can fix bugs faster. The data contains no personal information (no email, no pilot ID, no PIREP content). [Enable] [Decide later]"

The pilot chooses:
- **"Enable"** → `error_reporting.enabled = true` persisted, Sentry SDK initialized, events sent from now on
- **"Decide later"** → `error_reporting.enabled` stays `false`, no more banner on the next start, pilot can enable it manually in settings

The pilot can revoke at any time in settings — takes effect immediately (see DS7, Contract Section 9.1).

**Rationale:**
- **GDPR Art. 6(1)(a) (consent)** — the pilot actively consents, documented by persisting the `true` value with a timestamp in `config.json`
- Art. 6(1)(f) (legitimate interest) would theoretically be possible, but is a weaker legal basis than explicit consent given an opt-in default
- The pilot can revoke at any time without giving a reason (GDPR Art. 7(3))
- **Consistency requirement:** default-OFF applies in ALL three sources (this spec's LE4, Telemetry Contract Section 7, roadmap table). In case of contradiction between sources, the Telemetry Contract wins.

### LE5 — Anonymization: NO Pilot ID, NO Emails, NO Tokens

The Sentry SDK is configured so that:
- The `beforeSend(event)` hook removes all known PII fields
- Tokens (phpVMS API key, bearer auth) are stripped from stacks/breadcrumbs
- The pilot ID is transmitted as an anonymized hash (= "pilot-23" → SHA256("salt+23") → first 8 characters)
- Aircraft registration is transmitted (not PII)
- Flight number is transmitted (not PII)
- HTTP requests are reduced to URL + status code (= body is not sent)

**Rationale:**
- Respect pilot privacy
- GDPR argumentation is much simpler
- Prevents login tokens from accidentally landing in GlitchTip

### LE6 — Custom Events for Non-Crash Cases

Not only classic exceptions, but also our existing activity log WARN/ERROR entries go to GlitchTip via `Sentry.captureMessage()`. Specifically:

- Every `log_activity_handle(state, ActivityLevel::Error, ...)` additionally calls `sentry::capture_message(msg, Level::Error)`
- Every `log_activity_handle(state, ActivityLevel::Warn, ...)` with selected codes (e.g. PIREP errors, aircraft mismatch, auto-start skip) likewise
- Custom events for "interesting" forensics findings (bounce forensics, etc.) — see LE7

**Rationale:** "Pilot cannot start" is the more important class of errors than "app crashes". We want to see both.

### LE7 — Don't Send Forensics Events for Every Landing, Only "Interesting" Ones

Sending a forensics event to GlitchTip for every touchdown would be data spam. Instead, a filter:

- **Hard Landing** (vs < -600 fpm or peak_g > 1.7): event with full forensics
- **Light bounce forensic-only** (= bounce_count=0 but forensic_bounce_count>0): event with bounce details — so we see Adrian-class issues early
- **Hard Bounce** (scored_bounce_count >= 2): event
- **DDS violation** (touchdown before displaced threshold): event
- **Wing strike risk** (bank > max_bank_landing_deg × 90%): event

Normal "good" landings produce NO Sentry events.

**Rationale:** the Sentry free tier has no event limits, but we don't want to clutter the triage inbox. Only "worth someone looking" events.

### LE8 — Release Tag = AeroACARS Version, Not Build Hash

Every Sentry event carries `release: aeroacars-client@0.9.0` (not `release: a7b3f9c2`). This makes GlitchTip group by official versions, not by individual builds.

**Rationale:**
- Pilots run on official versions (= auto-updater installs v0.9.0 etc.)
- Release health (= "99.2% crash-free in v0.9.0") becomes measurable
- Diff between versions visible ("v0.9.0 has 12 bugs, v0.8.4 had 8")

### LE9 — Discord Webhook for New Issues

GlitchTip can fire a webhook per new issue class. We set up a GSG Discord channel `#aeroacars-bugs` and configure GlitchTip to point there.

Trigger:
- New issue class (= bug type GlitchTip hasn't seen yet)
- Spike (= bug frequency doubles within 1h)
- Regression (= a bug that was marked "resolved" reappears)

Non-triggers (otherwise spam):
- Every single event of a known bug

**Rationale:** Discord notifications only when there's SOMETHING NEW — no duplicate notifications for the same bug class.

### Client Rust (`client/src-tauri/src/main.rs`)

```rust
fn main() {
    // Sentry init must happen BEFORE Tauri setup
    let _guard = sentry::init((
        env!("SENTRY_DSN_CLIENT"),  // = compile-time via build.rs from env
        sentry::ClientOptions {
            release: sentry::release_name!(),
            // Anonymization: filter out all PII
            before_send: Some(Arc::new(|mut event| {
                // Strip tokens from breadcrumbs
                for crumb in event.breadcrumbs.iter_mut() {
                    if let Some(data) = &mut crumb.data {
                        data.remove("token");
                        data.remove("password");
                        data.remove("authorization");
                    }
                }
                // Hash user IDs
                if let Some(user) = &mut event.user {
                    user.email = None;  // Email NEVER transmitted
                    user.username = None;
                    user.id = user.id.as_ref().map(|id| {
                        let hash = blake3::hash(format!("aeroacars-pii-salt-{}", id).as_bytes());
                        Some(hex::encode(&hash.as_bytes()[..4]))
                    }).flatten();
                }
                Some(event)
            })),
            environment: Some(if cfg!(debug_assertions) { "dev".into() } else { "production".into() }),
            ..Default::default()
        },
    ));

    aeroacars_app_lib::run()
}
```

### Client Rust — Custom Events for Activity Log

```rust
// in log_activity_handle (lib.rs:~4350):
fn log_activity_handle(
    app: &AppHandle,
    level: ActivityLevel,
    message: impl Into<String>,
    detail: Option<String>,
) {
    let msg = message.into();
    // Existing path to the ACARS log tab
    log_activity(&app.state::<AppState>(), level, msg.clone(), detail.clone());

    // NEW v0.9.0: for WARN/ERROR additionally to Sentry/GlitchTip
    if matches!(level, ActivityLevel::Warn | ActivityLevel::Error) {
        sentry::with_scope(
            |scope| {
                // Context tags
                if let Some(flight) = app.state::<AppState>().active_flight.lock().unwrap().as_ref() {
                    scope.set_tag("callsign", format_callsign(&flight.airline_icao, &flight.flight_number));
                    scope.set_tag("dep", &flight.dpt_airport);
                    scope.set_tag("arr", &flight.arr_airport);
                    scope.set_tag("aircraft", flight.planned_aircraft_icao.as_deref().unwrap_or("?"));
                }
                if let Some(snap) = current_snapshot(app) {
                    scope.set_tag("simulator", snap.simulator.label());
                }
                if let Some(d) = detail {
                    scope.set_extra("detail", d.into());
                }
            },
            || {
                sentry::capture_message(
                    &msg,
                    if matches!(level, ActivityLevel::Error) {
                        sentry::Level::Error
                    } else {
                        sentry::Level::Warning
                    },
                );
            },
        );
    }
}
```

  dsn: import.meta.env.VITE_SENTRY_DSN_CLIENT_FRONTEND,

## Which Events Do We Track Concretely?

### Tag Allowlist (= the ONLY thing that may land as tag/extra/context in the event)

Every Sentry event MUST draw its tags from this allowlist. Tags not listed here are discarded by the `before_send` hook before sending. Defense-in-depth against accidental PII leaks through future code changes.

| Tag name | Type | Source (owner per Contract Section 3) | Example | Sanitization |
|---|---|---|---|---|

### Redaction Rules per Event Class (= what gets REDACTED, never sent)

Every event class has a curated value selection. Here's the explicit negative list per event type — enforced by the `before_send` hook:

| Event class | Fields that must go (redaction) | Rationale |
|---|---|---|
| **Panic / Crash** | `panic_payload`, `local_var_values`, `arg_values` in stack frames | can contain lat/lon/tokens |
| **PIREP File Failed (transient + hard)** | `response_body`, `request_body`, `headers.authorization`, `headers.cookie`, `url.query` | response body may contain pilot details; request body contains PIREP notes; auth header contains a token |
| **Aircraft Mismatch** | `bid_object`, `sim_snapshot`, `pilot_object` | full snapshots can contain PII; only ICAO tags are enough |
| **Auto-Start: no match** | `bids[]` array, `lat`/`lon`, exact `distance_m` | tag `error.code=no_bid_match` is enough; distance in coarse buckets (`< 5nm` / `5-50nm` / `> 50nm`) |
| **not_at_departure** | `lat`/`lon`, exact `distance_nm` | tag `error.code=not_at_departure` + distance bucket is enough |
| **Forensic-only Bounce** | `samples[]`, `lat`/`lon` | tag `bounce.max_agl_ft` + `aircraft` is enough; full sample history is not relevant for bug triage |
| **Hard Landing** | `samples[]`, `lat`/`lon`, `aircraft_title` | tags `vs.fpm`, `peak_g`, `aircraft` (= ICAO) are enough |
| **DDS Violation** | `lat`/`lon`, `runway_geometry_object` | tag `airport` + `runway` is enough |
| **SimConnect Disconnect** | `pipe_path`, `os_error_message_full`, `local_paths` | pipe path can contain the user's directory; tag `error.kind=sim_disconnect` + bucketed counter is enough |
| **Webapp React Errors** | full `componentStack`, `props_object`, `state_object` | component stacks are ok, but props/state can contain PIREP notes; only `error.code=react_error` + component name |
| **Recorder DB Errors** | `query_full`, `bind_values[]` | bind values can contain pilot IDs etc.; tag `error.kind=db_error` + `query.type=SELECT/INSERT/...` (= verb only, not the statement) |
| **Recorder MQTT Errors** | `topic_full`, `payload_full`, `payload_size_bytes` | topic contains pilot ID (= `aeroacars/gsg/23/...`); tag `error.kind=mqtt_error` + `topic.channel` (= only "position"/"status"/"phase", not the pilot ID) |

**Allowlist enforcement in code:**

```rust
// in client/src-tauri/src/sentry_redaction.rs (NEW v0.9.0)
const ALLOWED_TAG_KEYS: &[&str] = &[
    "os", "os.version",
    "app.version", "app.component",
    "simulator", "aircraft", "airport", "runway",
    "pilot.hash", "pirep.id", "callsign", "route", "phase",
    "forensics.version",
    "error.code", "error.status_code", "error.kind",
    "feature.flag",
    "distance.bucket",  // bucketed, not exact
];

pub fn redact_tags(tags: &mut HashMap<String, String>) {
    tags.retain(|k, _| ALLOWED_TAG_KEYS.contains(&k.as_str()));
}
```

Called in the `before_send` hook before the event is passed to the Sentry SDK. Defense-in-depth: even if a developer accidentally calls `event.set_tag("user.email", ...)`, the tag would be stripped out.

## Open Decisions

1. **Subdomain vs. path?** `tip.kant.ovh` (simple, separate logs) vs. `live.kant.ovh/glitchtip` (one domain) — proposal: subdomain for clarity
2. **Sample rate < 100%?** At 30+ pilots, potentially sample performance events at 10% rate — for now 100%, scale later
3. **Email notifications to us?** GlitchTip can also send email in addition to Discord — proposal: Discord ONLY (email would become spam)
4. **Pilot hash salt rotation?** If the salt changes, we "lose" trend data per pilot — proposal: set the salt once, never change it
5. **Auto-cleanup retention:** GlitchTip can delete old events after 30/60/90 days — proposal: 30 days (to save VPS disk)
