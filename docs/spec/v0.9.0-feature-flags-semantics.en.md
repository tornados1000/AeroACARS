# v0.9.0 — Feature Flag Semantics (Defaults, Persistence, Kill Switch)

**Status:** PROPOSAL — extension of Telemetry Contract Section 7
**Date:** 2026-05-18
**Source:** QA-round-3 finding ("Feature flags table is a short form — defaults, persistence, UI visibility, migration, kill switch, and data behavior on disable are missing per flag")
**Goal:** Fully specify each flag from `v0.9.0-telemetry-contract.md` Section 7: default value, persistence location, UI visibility, remote-vs-local, migration behavior v0.8.4 → v0.9.0, behavior on disable after data has already been generated, and the kill-switch path.

## Mandatory Rule — Cross-Reference

This document is **NOT a consumer spec** but an **extension** of the telemetry contract. Specifically:

- **Reference document:** `docs/spec/v0.9.0-telemetry-contract.md` Section 7 "Feature Flags / Rollout Gates" (8 flags in tabular short form)
- **Precedence order:** Telemetry contract > this spec > detail specs. This spec refines the short-form table but does not change flag names or defaults from the short-form table. If a detail in this spec conflicts with the contract, the contract is authoritative.
- **Sync requirement:** Any change to the flag table in the contract must update this spec IN THE SAME PR. Otherwise, roll back.
- **Consumers:** This spec is read by the implementation sprint for the settings UI, by QA for test cases, and by the release pipeline for migration smoke tests.

## Summary — Why Kill-Switch Semantics Are Critical

The 8 v0.9.0 feature flags control behavior that can become critical in two classes:

1. **External side effects with privacy impact** — GlitchTip and Discord RPC send data to third-party systems (own VPS or the Discord client, respectively). If a bug occurs there (e.g. "Discord RPC sends pilot_id unhashed despite the anonymization flag"), it must not have to wait for the next app release to be fixed. The pilot or VA admin needs an emergency path to "turn it off within 5 minutes."
2. **Data generation with consistency impact** — Per-bounce and expanded phases generate new fields in PIREPs. If a flag is switched off mid-sprint (e.g. "GO_AROUND is misdetected, causing 50 phantom go_around_events in the web app"), this must not cause mixed-state data corruption. Clearly defined "disable after data generated" semantics protect the historical PIREP record.

Without explicit semantics, typical bugs of this class happen:
- "Pilot disabled GlitchTip in settings, but the app keeps sending because the settings cache is stale"
- "The per-bounce flag was disabled on day 3, old PIREPs show an empty bounces[] even though data exists"
- "Discord RPC bug on live release day, no kill switch other than a new release"

This spec mandates these paths.

## General Principles

### P1. Single Source of Truth per Flag

Each flag has **EXACTLY ONE storage location** and **EXACTLY ONE read function**. Multiple caches are forbidden. Specifically:

- Read function: `feature_flag::get<T>(key: &str) -> T` (Rust) resp. `useFeatureFlag<T>(key)` (React)
- Write function: `feature_flag::set<T>(key: &str, value: T) -> Result<(), Error>` (Rust)
- Both functions are the ONLY paths — components must not read the storage location directly.
- Rationale: if a flag is changed mid-flight, it's guaranteed that the next `get` returns the new value (= no memoization inconsistency).

### P2. Persistence Strategy — `config.json` as the Central File

**Decision:** We use the existing `config.json` in the Tauri app-data path (`%APPDATA%/AeroACARS/config.json` on Windows, `~/Library/Application Support/AeroACARS/config.json` on macOS). No separate `feature-flags.json`.

**Rationale:**
- **For a central `config.json`:** the existing settings UI already reads/writes there (SimBrief settings, MQTT config). The pilot finds all options in one place. Backup is a single file. Migration is a schema bump.
- **Against a separate `feature-flags.json`:** would duplicate tooling (two JSON schemas, two validations, two backup paths) with no clear benefit. Power users want to open one editor, not two.
- **Power-user editing:** the file is plain JSON with a schema version. Edit-with-Notepad is supported (emergency path K2 below).

**Schema versioning:** `config.json` gets a top-level field `"schema_version": 2` (v0.8.4 had implicit version 1 with no explicit marker). On the first start after a v0.9.0 upgrade, a migrator runs (see "Migration Paths" section) that transforms schema 1 → schema 2 and writes the backup `config.json.v1.bak`.

### P3. Migration Strategy — Conservative Inherit + Explicit New Defaults

On upgrade from v0.8.4 to v0.9.0:

- **Existing keys** (SimBrief, MQTT, approach-stable config) are **carried over losslessly** — no defaults overwritten.
- **New flags** are written with the default defined in the contract. Flag values from the set of 8 are not present in the backup (= they were hardcoded or didn't exist at all in v0.8.4).
- **Unknown keys** in the old config.json are preserved during migration (= forward compat in case someone manually added a field).
- **Schema bump:** `schema_version` is increased from 1 → 2 ONLY if the migration completes without errors. On a migrator crash, v1 stays and the v0.9.0 start fails with a clear error message in the activity log + a modal.

### P4. Emergency Paths (Kill-Switch Classification)

Three classes of kill switches with different latency and permission requirements:

| Class | Path | Latency | Permission | Use Case |
|---|---|---|---|---|
| **K1** | Settings UI toggle | effective in <5s | Pilot themselves | Normal opt-out |
| **K2** | `config.json` edit + app restart | 1-2 min | Pilot themselves (power user) | UI bug or pre-crash disable |
| **K3** | VA Discord broadcast "please turn off now" | 5-30 min (manual, depends on pilot) | VA admin | Live-bug emergency without a remote channel |

**Deliberately NOT included in v0.9.0:** a remote push channel (e.g. "VA admin sets a flag for all pilots simultaneously"). See "Out of Scope" — rationale: a remote push would require auth + push-channel management + acknowledgment tracking + conflict resolution, that's a spec of its own. The manual path K3 is sufficient for the VA's size (3-15 active pilots, all reachable in one Discord).

### P5. Defensive Defaults

When there's a conflict between "pilot convenience" and "privacy risk", the following applies:

- Privacy-relevant flags (= external data path: GlitchTip, Discord RPC) are **off by default**, explicit pilot opt-in.
- Convenience flags (= pure pilot-client behavior optimization: delta sampling, expanded phases, per-bounce) are **on by default**.
- Anonymization flags are **on by default** (= conservative choice: better too little tracking than too much).

## Per-Flag Sections

### F1. `position_sampling.delta_enabled` — Delta Sampling

**Detail spec:** `v0.9.0-delta-position-sampling.md`

| Aspect | Value |
|---|---|
| **Default, fresh install v0.9.0** | `true` |
| **Default on upgrade from v0.8.4** | `true` (new key, didn't exist in v0.8.4) |
| **Persistence location** | `config.json` → `position_sampling.delta_enabled` |
| **UI visibility** | Standard user tab "Connection & Stream" — visible, no power-user mode needed |
| **Remote/Local** | Local per pilot. No remote path in v0.9.0 |
| **Effective latency** | Immediate (= no app restart). The streamer tick reads the flag on every tick |
| **UI warning** | "Default is ON. Turning it off increases bandwidth and recorder DB growth by a factor of ~5" |

**Migration on upgrade v0.8.4 → v0.9.0:**
- The key doesn't exist in v0.8.4 → is written as `true` on the first v0.9.0 start (= new default)
- A pilot who explicitly wants v0.8.x behavior can set it to `false` after upgrading
- Activity log on first start: "Delta sampling enabled (new in v0.9.0). Settings → Connection & Stream"

**Behavior on disable after data has already been generated:**

| Data class | What happens | Pilot-client UI view | Web-app UI view |
|---|---|---|---|
| Position samples already sent to the recorder DB | Remain unchanged (sparse) | n/a (stream data) | The live map shows old sparse samples just as before |
| Future samples | Fixed-rate tick every 5-8s | n/a | Live map denser |
| Historical PIREPs | unchanged | unchanged | unchanged |

→ **Data is not deleted.** A mixed state (= sparse historical + dense new samples after disable) is acceptable because position-stream data is temporary (30-day retention).

**Kill-switch path:**
- **K1 (UI):** Settings → Connection & Stream → toggle "Delta Sampling". Effective immediately, no restart
- **K2 (config.json):** `position_sampling.delta_enabled = false`. App restart not strictly required, but recommended so the streamer reloads the value
- **K3 (emergency):** "All pilots: please disable delta sampling in settings" — typical when a recorder DB schema mismatch occurs on the server

### F5. `forensics.per_bounce_enabled` — Per-Bounce JSON Detail

**Detail spec:** `v0.9.0-per-bounce-detail.md`

| Aspect | Value |
|---|---|
| **Default, fresh install v0.9.0** | `true` |
| **Default on upgrade from v0.8.4** | `true` |
| **Persistence location** | `config.json` → `forensics.per_bounce_enabled` |
| **UI visibility** | Advanced tab → "Landing Forensics" — visible |
| **Remote/Local** | Local per pilot |
| **Effective latency** | Immediate. The touchdown detector reads the flag at the touchdown edge |
| **UI warning** | "Default is ON. When OFF, you lose the detail records per bounce — the counter (`bounce_count`) is retained (= v0.8.x behavior)" |

**Migration on upgrade v0.8.4 → v0.9.0:** New key → default `true`. The touchdown detector continues to work as in v0.8.x when the flag = false.

**Behavior on disable after data has already been generated:**

This is the **most critical disable case** because PIREPs get a new persistent field.

| Data class | What happens | Pilot-client UI view | Web-app UI view |
|---|---|---|---|
| `bounces[]` already generated in old PIREPs | Remain in `landing_history.json` AND in the recorder DB's `payload_json` | LandingPanel's detail modal keeps working for old PIREPs unchanged (read path is `record.bounces ?? []`, so an empty array for new disable files) | LandingAnalysis keeps showing the old bounce tables |
| Future landings | `bounces[]` is NOT written to the `touchdown` payload. `bounce_count` (legacy field) remains | LandingPanel shows only the counter "3 Bounces", no detail-modal button | ditto |
| Future PIREPs | No `bounces` field in payload_json | ditto | ditto |

**Important — consistency guarantee:** if the pilot toggles the flag intermittently (= day 1 ON, day 2 OFF, day 3 ON), some PIREPs will have `bounces[]` and some won't. This is **not a bug** — the read path handles both cases (see Telemetry Contract Section 5 "Backward-Compat Matrix").

**Kill-switch path:**
- **K1:** Settings → Advanced → Landing Forensics → "Enable Per-Bounce Detail"
- **K2:** `forensics.per_bounce_enabled = false`
- **K3:** "The per-bounce detector writes faulty records (= bounce_max_agl contradicts max(bounces[].max_agl_ft))" → broadcast "please disable until v0.9.1"

### F6. `error_reporting.enabled` — GlitchTip Error Reporting

**Detail spec:** `v0.9.0-glitchtip-self-hosted.md`

| Aspect | Value |
|---|---|
| **Default, fresh install v0.9.0** | **`false`** (opt-in!) |
| **Default on upgrade from v0.8.4** | **`false`** — even if the pilot is an "experienced beta tester", no automatic opt-in |
| **Persistence location** | `config.json` → `error_reporting.enabled` |
| **UI visibility** | Standard user tab "Privacy & Telemetry" — prominently visible with a detailed explanation |
| **Remote/Local** | Local per pilot |
| **Effective latency** | On toggle ON: the Sentry SDK is initialized immediately. On toggle OFF: the Sentry SDK is deinitialized immediately (= the running in-memory buffer is discarded, no flush to the server) |
| **UI warning** | "Default is OFF. When ON, you send anonymized crash and error reports to `tip.kant.ovh`. See the privacy page for details" |

**Special — boot behavior:**
- If `false`: the Sentry SDK is NOT initialized. `init_sentry()` is not even called. No DSN in memory.
- If `true`: Sentry SDK init with the DSN from the build env (= compiled into the binary, no runtime secret risk).

**Migration on upgrade v0.8.4 → v0.9.0:**
- v0.8.4 had no GlitchTip → there's nothing to inherit. Default `false` protects against unintended opt-in.
- On the first start after upgrade, the settings panel shows a **one-time banner**: "New in v0.9.0: GlitchTip crash reports. Default is OFF. Opt in here if interested." Banner dismisses after a click or a visit to settings.

**Behavior on disable after data has already been generated:**

| Data class | What happens | Pilot-client UI view | GlitchTip web view |
|---|---|---|---|
| Events already sent to Sentry | Remain in GlitchTip Postgres (30-day retention via the GlitchTip spec) | n/a (server data) | Admin keeps seeing old events |
| In-memory buffer (= not-yet-sent events) | DISCARDED on disable, not flushed | n/a | nothing new |
| Future crashes | NO Sentry event. The app's own activity-log WARN/ERROR path remains unchanged | unchanged | nothing |

**Server-side data deletion:** the pilot can file a deletion request via the privacy page + email to the admin (= GDPR Art. 17). No automatic deletion path in v0.9.0 — manual VPS path.

**Kill-switch path:**
- **K1:** Settings → Privacy & Telemetry → toggle "Send crash and error reports to GlitchTip". **Effective immediately — no app restart required (DS7 requirement from Telemetry Contract Section 9).** Implementation requirement: `sentry::close()` is called on toggle-off (= the Sentry Rust SDK supports this since v0.32, [docs.rs/sentry](https://docs.rs/sentry/latest/sentry/fn.close.html)). The local Sentry buffer is DISCARDED, not flushed. On the next toggle-on, Sentry is re-initialized.
- **K2:** `config.json` edit: `error_reporting.enabled = false`. App restart NOT strictly needed — the settings watcher re-reads the flag per tick. Restart as a power-user option if the settings UI hangs.
- **K3 — emergency (critical live bug):** Discord broadcast "please disable Privacy & Telemetry immediately" → pilots click Settings → toggle off → effective immediately (see K1). If pilots are unreachable: VPS-side emergency path: the GlitchTip endpoint is set to 503 → SDK POSTs fail → pilots notice nothing, data doesn't go out.
- **K3 — extreme emergency (VPS stop):** `systemctl stop glitchtip` on the VPS → all SDKs fail on POST → pilots notice nothing (no UI effect), but data doesn't go out.

**Why the "effective immediately" requirement:** DS7 (Telemetry Contract Section 9) explicitly states: "Opt-out works immediately, without an app restart." This is a privacy requirement — the pilot must be able to withdraw their consent at any time, and it must take effect IMMEDIATELY. A "restart recommended" note would undermine the privacy validity of the toggle.

### F7. `integrations.discord_rpc.enabled` — Discord Rich Presence

**Detail spec:** `v0.9.0-discord-rich-presence.md`

| Aspect | Value |
|---|---|
| **Default, fresh install v0.9.0** | **`false`** (opt-in!) |
| **Default on upgrade from v0.8.4** | **`false`** |
| **Persistence location** | `config.json` → `integrations.discord_rpc.enabled` |
| **UI visibility** | Standard user tab "Integrations" — visible with a "Discord must be installed" note |
| **Remote/Local** | Local per pilot |
| **Effective latency** | On toggle ON: the DiscordPresenceManager is initialized immediately (= IPC connect to the local Discord client). On toggle OFF: the Discord status is cleared immediately (within 5s, see DS8 in Telemetry Contract Section 9) |
| **UI warning** | "Default is OFF. When ON, your Discord profile shows your current flight status. See the privacy page for the displayed fields" |

**Special — sub-flag `integrations.discord_rpc.anonymize_callsign`:**
- Default `true` on fresh install + upgrade
- If `true`: the state text shows "GSG flight" instead of "GSG3184"
- If `false`: the full callsign is visible
- Shown in the same sub-section of the settings tab, only visible when `discord_rpc.enabled = true`

**Migration on upgrade v0.8.4 → v0.9.0:**
- New top-level key `integrations.discord_rpc` → the entire sub-object is written with defaults (= `{ enabled: false, anonymize_callsign: true }`)
- A pilot already using another Discord bot (e.g. SimToolkitPro) is notified in settings: "Note: enabling this may conflict with other RPC apps — Discord only shows one source at a time"

**Behavior on disable after data has already been generated:**

Discord RPC is **live-only** (see Telemetry Contract Section 4: "Discord activity state: live-only, persisted nowhere"). Therefore:

| Data class | What happens | Pilot-client UI view | Discord view |
|---|---|---|---|
| Currently displayed Discord status | Cleared within 5s (= `clear_activity()` call) | Settings shows "status cleared" | Profile no longer shows an RPC status |
| Activation history | n/a (no logging in the DB) | n/a | n/a |
| Other pilots / VA server | n/a — RPC is local to the Discord client, no server-side state | n/a | n/a |

→ **No data question** because Discord RPC produces no persistent data.

**Kill-switch path:**
- **K1:** Settings → Integrations → toggle "Discord Rich Presence"
- **K2:** `integrations.discord_rpc.enabled = false`. Restart recommended if the DiscordPresenceManager hangs erroneously
- **K3 — extremely fast due to IPC crash risk:** Discord RPC is the **most likely source of a live-bug emergency** (third-party IPC to a foreign process). Emergency paths:
  - Discord broadcast "please disable Discord RPC immediately + restart"
  - **Sub-flag override via VPS webhook (NOT in v0.9.0):** would be possible but deliberately not built, see "Out of Scope"
  - **Fallback if a pilot is unreachable:** disable the Discord Application ID on the Discord Developer Portal → IPC connect fails → the RPC manager logs an error in the activity log and continues (no app crash). Effectively: the status disappears for all pilots within one Discord restart cycle (≤ 60s)

### F8. `error_reporting.anonymize_pilot_id` — Hash Function On/Off

**Detail spec:** `v0.9.0-glitchtip-self-hosted.md` (privacy section)

| Aspect | Value |
|---|---|
| **Default, fresh install v0.9.0** | `true` |
| **Default on upgrade from v0.8.4** | `true` (new key) |
| **Persistence location** | `config.json` → `error_reporting.anonymize_pilot_id` |
| **UI visibility** | **Power-user mode** (= hidden behind an "Advanced Settings" toggle in the privacy tab) |
| **Remote/Local** | Local per pilot |
| **Effective latency** | Immediate on the next Sentry event (= the tag computation reads the flag per event) |
| **UI warning** | **"NOT RECOMMENDED TO DISABLE.** When OFF, your pilot_id is sent unhashed to GlitchTip — only for local tests against `localhost:9000`. In production (= tip.kant.ovh) the hash remains mandatory." |

**Special — server-side enforcement:**
- Even if a pilot sets this flag to `false`, the Sentry backend will **drop** an unhashed pilot_id tag (= a pre-processor hook in the GlitchTip config). That is the defense-in-depth layer. The client flag is therefore only relevant for debug sessions — no privacy loophole.
- Rationale for server-side drop: an unhashed pilot_id is GDPR-relevant, a client bug must not leak data

**Migration on upgrade v0.8.4 → v0.9.0:** New key → default `true`. The power-user section is collapsed on the first start (= the pilot doesn't even see the toggle).

**Behavior on disable after data has already been generated:**

| Data class | What happens | UI view | Server view |
|---|---|---|---|
| Events already sent (hashed pilot_id) | Remain in GlitchTip | n/a | Admin keeps seeing the hash |
| Future events after disable + with GlitchTip ON | The client would send an unhashed pilot_id — the server drops it | n/a | The tag is simply missing from the event |

→ **No data-consistency problem.** Hash and plain form are different tag values (= Sentry filtering must know both), but this is a search-convenience matter, not a bug.

**Kill-switch path:**
- **K1:** Settings → Privacy → "Show Advanced Settings" → toggle "Anonymize pilot_id"
- **K2:** `error_reporting.anonymize_pilot_id = false`
- **K3:** No real emergency path conceivable — anonymization protects the pilot, not the server. On a bug ("hash function crashes"), F6 (`error_reporting.enabled`) is knocked out entirely

| `forensics.per_bounce_enabled` | no | `true` |
| `error_reporting.enabled` | no | `false` (defensive default) |
| `integrations.discord_rpc.enabled` | no | `false` |
| `error_reporting.anonymize_pilot_id` | no | `true` |

**All 8 flags are new.** No inheritance logic needed — the migrator simply writes the defaults.

### What Happens on a Migration Error?

| Error | Behavior |
|---|---|
| Backup write fails (= disk full) | App start aborts, error modal "Please free up disk space or edit config.json manually" |
| Atomic write of the new v2 config fails | Backup remains, the old v1 config remains, the app starts with v1 (= no v0.9.0 flags available — flag reads return hardcoded defaults from `feature_flag::default(key)`) |
| A backup already exists (= 2nd upgrade attempt) | The backup is renamed with a timestamp (`config.json.v1.bak.2026-05-18T14-22-01`) |

### Downgrade v0.9.0 → v0.8.4 — What Happens?

**Decision:** the v0.9.0 config is read by v0.8.4 as "having unknown extra keys". v0.8.4 has NO schema-validation path and passively ignores unknown keys. Concrete behavior:

| Situation | v0.8.4 behavior |
|---|---|
| Pilot installs v0.8.4 over v0.9.0 (= downgrade) | v0.8.4 reads `config.json`, ignores `schema_version=2` and all 8 new flags. Existing keys (SimBrief, MQTT) keep working |
| v0.8.4 writes the config back (= pilot changes something in settings) | v0.8.4 SERIALIZES ONLY the keys it knows → the 8 v0.9.0 flags are lost. `schema_version` is lost |
| Pilot installs v0.9.0 again after the downgrade | The migrator sees a missing `schema_version` → runs again → writes the 8 flags with defaults. BUT: pilot customizations (e.g. "GlitchTip enabled") are lost → reset to default |

**Rationale for this decision:**
- **Pro:** schema versioning is trivial (1 field), no forward-compat complexity needed in v0.8.4 (which we can't change anymore anyway)
- **Con:** pilot customizations are lost on downgrade + re-upgrade
- **Acceptance:** downgrade is an emergency path. Losing pilot customizations during an emergency downgrade is acceptable. Whoever needs a downgrade already has bigger problems than flag settings

**A schema-versioned-config alternative was rejected** because it's overkill for v0.9.0 (would require a JSON-schema library, validator, multi-version migrator, and a test matrix for each schema version). We'll re-evaluate this topic at v1.0.0 once the number of flags increases.

## Kill-Switch Mechanisms — Consolidated Matrix

| Class | Path | Who | Latency | Usable for |
|---|---|---|---|---|
| **K1 — Settings UI** | Toggle in the settings panel | Pilot | 0-5s | Normal opt-out / opt-in |
| **K2 — config.json edit** | Edit the file with Notepad/VS Code | Pilot (power user) | 30-90s (= restart time) | UI bug prevents K1 / pre-crash disable |
| **K3a — VA Discord broadcast** | "please disable" + manual mute | VA admin | 5-30 min | Live bug, all pilots react manually |
| **K3b — server-side emergency brake** | Sentry endpoint 503 / stop GlitchTip | VA admin on the VPS | <2 min | GlitchTip-specific emergency (F6) |
| **K3c — disable the Discord app** | Discord Developer Portal | VA admin / Thomas | <5 min, effect within ≤ 60s | Discord-RPC-specific (F7) |
| **K4 — new build** | v0.9.0.1 with a hardcoded `false` | Maintainer | 24-48 h (build, sign, release) | Last escalation when K1-K3 aren't enough |

**NO remote-push path in v0.9.0.** Rationale:
- A push channel would need auth + ack + conflict resolution + a UI indicator for "flag was overridden remotely" — a spec of its own
- For the VA's size (3-15 active pilots), K3a (Discord broadcast) is sufficient
- K3b/c cover the two most likely live-bug classes (GlitchTip, Discord) on the server/third-party side


→ **5-min goal achieved** through the combination of K3a + K3c. No app update needed for the emergency brake, only for the final fix.

## Behavior on Disable After Data Has Been Generated — Consolidated Table

| Flag | Old data remains? | Pilot UI for old data | Web app for old data | Data deletion? |
|---|---|---|---|---|
| F1 Delta sampling | Yes (sparse positions in DB) | n/a — stream data | Live map shows sparse samples normally | No (regular 30d retention) |
| F2 RTO phase | Yes (`rto_event` in payload_json) | LandingPanel RTO indicator remains visible | RTO tab remains visible | No |
| F3 GO_AROUND | Yes (`go_around_events` in payload_json) | Phase history remains visible | Phase history remains visible | No |
| F4 DEBOARDING | Yes (phase=DEBOARDING in flight_events) | Activity log remains visible | Phase history remains visible | No |
| F5 Per-bounce | Yes (`bounces[]` in payload_json + landing_history.json) | Detail modal remains visible for old PIREPs | Detail table remains visible | No |
| F6 GlitchTip | Yes (on server, 30d retention) | n/a — no pilot-side persistence | n/a (pilot has no GlitchTip view) | GDPR deletion request via email to admin |
| F7 Discord RPC | No (live-only) | n/a | n/a | n/a |
| F8 Anonymize-pilot_id | Mixed state (hash + plain as different tag values) | n/a | n/a | Server-side drop of unhashed protects live data |

**Mandatory rule:** for EVERY flag, the read path in the UI/web app is **independent** of the current flag state. Displaying old data works even if the generating flag has been disabled. Concretely in code:

```ts
// React component — CORRECT
const bounces = record.bounces ?? [];
if (bounces.length > 0) {
  return <BounceDetailModal bounces={bounces} />;
}

// WRONG (anti-pattern):
const flagEnabled = useFeatureFlag('forensics.per_bounce_enabled');
if (flagEnabled && record.bounces) { ... }
// → would hide old data as soon as the flag is off
```

### TypeScript Side (`client/src/services/featureFlags.ts`)

```ts
import { invoke } from '@tauri-apps/api/tauri';
import { useEffect, useState } from 'react';

export type FlagKey =
  | 'position_sampling.delta_enabled'
  | 'phases.rejected_take_off_enabled'
  | 'phases.go_around_enabled'
  | 'phases.deboarding_enabled'
  | 'forensics.per_bounce_enabled'
  | 'error_reporting.enabled'
  | 'error_reporting.anonymize_pilot_id'
  | 'integrations.discord_rpc.enabled'
  | 'integrations.discord_rpc.anonymize_callsign';

export async function getFlag(key: FlagKey): Promise<boolean> {
  return invoke<boolean>('feature_flag_get', { key });
}

export async function setFlag(key: FlagKey, value: boolean): Promise<void> {
  return invoke('feature_flag_set', { key, value });
}

export function useFeatureFlag(key: FlagKey): boolean {
  const [value, setValue] = useState<boolean>(false);
  useEffect(() => {
    let cancelled = false;
    getFlag(key).then(v => { if (!cancelled) setValue(v); });
    const unlistenPromise = listen<{key: FlagKey, value: boolean}>(
      'feature-flag-changed',
      (e) => { if (!cancelled && e.payload.key === key) setValue(e.payload.value); }
    );
    return () => {
      cancelled = true;
      unlistenPromise.then(u => u());
    };
  }, [key]);
  return value;
}
```

## Out of Scope

The following is **deliberately not** in v0.9.0:

| Item | Rationale |
|---|---|
| **Remote config management server** | Requires auth + push channel + ack tracking + conflict resolution + a UI for a "remote-overridden" indicator. A spec of its own (candidate for v1.0). VA size (3-15 pilots) doesn't justify the effort |
| **A/B-testing infrastructure** | No user-base size that makes A/B tests statistically meaningful. If ever needed, as a later cloud-config extension |
| **Feature-flag analytics** | We don't want to track who toggled which flag when (= a privacy-conscious default stance). If a pilot needs help, ask on Discord |
| **Multi-profile support** | The pilot has exactly 1 config. Test vs. prod profile switching is not relevant |
| **Schema versioning > v2** | As long as we don't restructure flag concepts in v1.0, a one-time v1→v2 migrator is enough |
| **Forward-compat hooks** | v0.9.0 config can be extended additively in v0.9.x patches (= new keys with serde default). Schema bump only at v1.0 |
| **Per-flag audit log** | The activity log logs flag changes as a single-line info event. Full audit (= "when did who change which flag how") is out of scope |
| **Flag dependency graph** | e.g. "F8 may only be enabled when F6 is active." Currently the dependency is shown manually in the UI (= the F7 sub-flag box is only visible when F7=ON). A generic graph is overkill |
| **Pilot override by VA via VPS** | Would be nice for "please enable per-bounce for everyone for the QA sprint", but see remote config management above |
