# v0.7.18 Orphan Flight Cleanup — Spec

**Status:** PROPOSAL — ready for implementation after v0.7.17 release
**Date:** 2026-05-13
**Source:** GAF 152 incident from 2026-05-12 (Pilot 15 / Thomas K, JSON dump `flight-gsg-15.json`)
**Goal:** Pilot can clean up orphaned PIREPs/bids themselves. FSM gaps that let such orphans arise in the first place are closed. The touchdown display shows the real crash location instead of the planned destination.

## Summary

Four related bugs from the GAF-152 incident, which we deliberately kept out of v0.7.17 so the score/consistency fix could land cleanly. Now as its own patch:

| ID | What | Symptom |
|---|---|---|
| **B-011** | Orphan cancel UI | Pilot cannot clean up orphaned PIREPs/bids on phpVMS via the client when the client no longer has an active flight locally |
| **B-012** | TD airport field | A crash in the Baltic Sea is displayed as "landed at EDDB" (= planned destination), not as "off-airport touchdown near UMKK" |
| **B-013** | Sim position reset | The touchdown sampler swallows MSFS glitches (lat/lon → 0/0, altitude jump 50,000 ft) and logs a 14-G crash from them |
| **B-014** | `flight_cancel` file-first | Manual cancels in finalizable phases (LANDING / TaxiIn / BLOCKS_ON / Arrived with valid TD) try to cancel directly instead of attempting to file first. Prevents data loss + orphans when the pilot really just meant to "end" the flight. |

In addition, the spec cleanly defines three **deletion operations**:
- **PIREP cancel** (PIREP becomes CANCELLED, not submitted, aircraft is freed automatically)
- **Bid drop** (reservation is deleted)
- **Local forget** (clean up local client state without a phpVMS call)

## Why

### The GAF-152 Incident (Primary Source)

Reconstructed from the JSON dump:

| Time (UTC) | What |
|---|---|
| 19:09:57 | Session 717 starts: `GAF 152 / A400 / UMKK→EDDB`. `pirep_id=NULL` |
| ~19:54:14 | **Sim position reset** — lat/lon jumps to 0.007/0.000 (Null Island in the Gulf of Guinea), altitude 53,820 ft |
| 19:53:55 | Touchdown sampler fires: lat=54.83/lon=20.15 (Baltic Sea, 30 km before UMKK), bank −82°, 14 G, wing strike 1026%, rollout 25 m → **crash, not landing**. Displayed in the UI as "landed at EDDB" |
| 19:55:30 | Last heartbeat, session 717 |
| ~19:56–19:59 | Pilot resets in the sim back to UMKK, switches to A321/CFG 152 |
| 19:59:13 | Pilot manually cancels session 717 (via `flight_cancel` or `flight_forget` in the UI) and immediately starts session 718 (CFG 152 / A321 / UMKK→EDDB). The GAF-152 PIREP is marked CANCELLED via `cancel_pirep` — but this discards the near-complete landing (no file attempt first). Had the client done "file-first" (B-014), the flight would have been filed correctly. |

The pilot later reports: "My flight is stuck on phpVMS, I can no longer book the aircraft." In the AeroACARS client he only sees session 718, no cancel button for GAF 152 because it no longer exists locally.

### Where the Orphans Arise

Three paths through which a PIREP/bid gets "stuck" on phpVMS:

1. **Sim crash mid-flight** (GAF 152): Session aborts before BLOCKS_ON is reached, no auto-file fires.
2. **Manual cancel in a finalizable state** (GAF 152 secondary trigger): Pilot clicks "discard flight" even though the flight was actually nearly complete (LANDING / TaxiIn / BLOCKS_ON with valid TD). `flight_cancel` calls `cancel_pirep` directly without a file attempt → the PIREP becomes CANCELLED instead of FILED, and the flown performance is lost. B-014 addresses exactly this via the file-first refactor.
3. **Client crash between prefile and DB persist**: phpVMS receives the prefile PIREP, but the client fails to store the `pirep_id` in its local session table → on the next start, the client knows nothing about the existing PIREP.

### Who Pays

- **Pilot:** Aircraft marked as "in flight" on phpVMS, cannot rebook it. Frustration. Has to contact the VA admin or poke around in the phpVMS web UI themselves.
- **VA admin:** Support requests, inconsistent statistics (X PIREPs `IN_PROGRESS`, no pilot flying them).
- **AeroACARS perception:** "The tool doesn't work reliably" — once a flight gets stuck, the workflow feels broken.

## Guiding Decisions

### 1. The Pilot Gets an Emergency Latch, Not a Miracle Cure

The **cleanup path** (B-011) is the most important feature. Even if we fix all the root causes (B-013 + B-014) perfectly, there will always be edge cases where a PIREP gets stuck — network down during the prefile response, server-side bug, force-quit, etc. The pilot must **always** have a way out without needing the VA admin.

### 2. The Web App Wins for the Touchdown Display

For the TD airport (B-012), the truth is unambiguous: **the value the TD coordinate points to**, not the planned destination code. The pilot client and web app must use the same path — `runway_match` first, then nearest airport within a 25-nmi radius, then only `flight.arr_airport` as the last fallback.

### 3. Sim Reset Detection Is Sample Hygiene, Not a Score Fix

B-013 discards contaminated samples instead of trying to "rescue" them. A single frame with lat/lon ≈ 0/0 is never the real touchdown — discard and move on, no reverse-engineering. Edge state (prev_in_air, sampler_touchdown_at) is NOT updated, so no phantom touchdown is triggered after the reset.

### 4. `flight_cancel` Tries to File First When the Flight Is Nearly Complete

B-014 does not add an automatic F7 hook (there isn't one — F7 in `apply_pause_resume` only produces a warning log, not a session reset). Instead, `flight_cancel` is refactored to "file-first, cancel-second":

- When `is_finalizable` (phase = LANDING/TaxiIn/BLOCKS_ON/Arrived + valid TD), `flight_cancel` first calls `attempt_auto_file`.
- The helper returns an **outcome**: `Filed` (submitted cleanly), `Queued` (transient error, placed in pirep_queue for a later retry), or `HardFailed` (validation/auth error, retry not sensible).
- **Only on `HardFailed` with `code != "blocked"`** may the cancel path proceed. `Queued` is NOT cancelled, otherwise we'd have the next data-loss bug (pilot sees "Cancel" → clicks → but the PIREP was already placed in the queue → the queue retries successfully later → but the backend has already set CANCELLED). `HardFailed { code: "blocked" }` (401/403) is also not cancelled — `cancel_pirep` would return the same 401/403 there, so it wouldn't help. Instead: `Err(UiError("blocked", …))`, `state.active_flight` remains for a later retry after VA clarification.
- In the extended confirm dialog, the pilot can explicitly choose "discard anyway", which bypasses the file attempt — for crash scenarios where the file result shouldn't go into the flight record.

## B-011 — Orphan Cancel UI

### What the Pilot Sees Today

When a PIREP/bid is stuck on phpVMS AND the local client no longer has an active flight:
- **No banner**, no note in the activity log
- **Cockpit tab is empty** (shows "no active flight")
- **Bids tab** shows the aircraft as available or not, depending on VA config
- The pilot only notices when trying to rebook the aircraft → error from phpVMS

### What the Pilot Must See

**Where:** Dedicated section in the **Settings tab**, at the very bottom under "Flight cleanup / server reset". Not in the cockpit — that's for the active flight.

**Default state (everything clean):**
> ✓ *"No orphaned flights found on phpVMS."*
> [ Check again ]

**When something is stuck:**
> ⚠ **1 orphaned flight found on phpVMS**
>
> **GAF 152** — A400 — UMKK → EDDB
> Started: 2026-05-12, 19:09 UTC (3 h 11 min ago)
> Status on server: **IN_PROGRESS**
> Assigned aircraft: **D-AIAI** (A400)
> Open bid: **yes, bid ID 12345**
>
> [ Cancel flight & release aircraft ]   [ Details ]

**Confirm dialog (destructive=true):**
> ⚠ **Really cancel GAF 152?**
>
> The following will happen:
> • The PIREP will be marked **CANCELLED** on phpVMS (cannot be undone)
> • Aircraft **D-AIAI** will be freed and can be used by you or another pilot
> • The bid on GAF 152 will be deleted *(if present)*
> • **No** PIREP will be submitted for the flown segment — the crash will not remain as an entry in your flight record

>
> [ Cancel ]   [ **Yes, discard flight** ]

**While processing:** Spinner.

**On success:** Green notice "✓ Flight cancelled, D-AIAI available again" + row disappears from the list + activity log entry.

**On error:** Red error message with error code (e.g. "phpVMS 404: PIREP no longer exists — clean up locally?" with its own [ Forget locally ] button).

### Backend API Operations

Three Tauri commands are required:

#### `flight_list_orphans() -> Vec<OrphanFlight>`
- Calls `client.get_user_pireps()` (already exists at [api-client/src/lib.rs:1060](client/src-tauri/crates/api-client/src/lib.rs:1060)).
- Filters for `state == 0` (IN_PROGRESS) AND not the locally active flight.
- Cross-references with **`client.get_bids()`** ([api-client/src/lib.rs:1053](client/src-tauri/crates/api-client/src/lib.rs:1053)) to find the matching bid per PIREP. (NOT `get_user_bids()` — that doesn't exist.)
- Returns a typed `OrphanFlight` array:
  ```rust
  pub struct OrphanFlight {
      pub pirep_id: String,
      pub bid_id: Option<i64>,
      /// phpVMS `flight_id` (alphanumeric, e.g. "flightid_1") — needed
      /// for the `{ flight_id }` fallback body in `delete_bid`
      /// (see API inventory). If None: only the `{ bid_id }` path is
      /// usable.
      pub flight_id: Option<String>,
      pub flight_number: Option<String>,           // from PirepSummary
      pub airline_id: Option<i64>,                 // from PirepSummary (not ICAO!)
      pub dpt_airport: Option<String>,             // from PirepSummary
      pub arr_airport: Option<String>,             // from PirepSummary
      pub aircraft_id: Option<i64>,                // from PirepSummary (numeric)
      pub aircraft_icao: Option<String>,           // → see note below
      pub aircraft_registration: Option<String>,   // → see note below
      pub started_at: Option<DateTime<Utc>>,       // → see note below
      pub age_minutes: Option<i64>,
  }
  ```

**Important data-path note — `PirepSummary` is deliberately lean:**

[`PirepSummary`](client/src-tauri/crates/api-client/src/lib.rs:884) currently contains only `id`, `airline_id`, `flight_number`, `aircraft_id`, `state`, `status`, `dpt_airport_id`, `arr_airport_id`. **Not** present: `started_at`, `aircraft_icao`, `aircraft_registration`, `created_at`.

Three options for enriching aircraft and timestamp data:

1. **Extend `PirepSummary` with the missing fields** and add the `GET /api/user/pireps` response fields with `#[serde(default)]` — if phpVMS provides them (must be verified live against `german-sky-group.eu` and `live.kant.ovh`). Preferred — fewer round trips.

2. **Make an additional `GET /api/pireps/{id}` per PIREP**, which returns the full PIREP resource (with the `aircraft` relation and `created_at`). More calls, but guaranteed complete data. Trade-off: with 20 orphans, 20 additional requests.

3. **Aircraft lookup via `client.get_user_fleet()`** (exists) — `aircraft_id` → subfleet resolution. ICAO + registration come from the fleet response. One additional request, then a local lookup.

**Preliminary decision:** Try option 1 first (spike: what does phpVMS actually deliver here?), option 3 as a safe fallback if the `PirepSummary` extension yields nothing new server-side. Option 2 only if both fail.

`started_at` is in any case the most important value (for "X h Y min ago" in the UI). If phpVMS delivers no `created_at`, we fall back on the numeric `id` as a sort key and show just "IN_PROGRESS" as the status instead of age.

#### `flight_cancel_orphan(pirep_id: String, bid_id: Option<i64>, flight_id: Option<String>) -> Result<(), UiError>`

The Tauri command signature takes **three** optional parameters — they come directly from the `OrphanFlight` struct returned by `flight_list_orphans`. The frontend passes them through 1:1:

```typescript
await invoke("flight_cancel_orphan", {
  pirepId: orphan.pirep_id,
  bidId: orphan.bid_id,        // Option<i64> → number | null
  flightId: orphan.flight_id,  // Option<String> → string | null
});
```

- **Sequential** (NOT parallel) calls in the following order:
  1. `client.cancel_pirep(&pirep_id)` → server cancels PIREP (state 0 → 3 CANCELLED). The phpVMS standard route is `DELETE /api/pireps/{pirep_id}/cancel`, with `PUT` as the phpVMS fallback. The current client still uses `POST` and needs to be corrected here.
  2. **If `bid_id.is_some()` OR `flight_id.is_some()`**: `client.delete_bid(bid_id, flight_id.as_deref())` → delete bid. The phpVMS standard route is `DELETE /api/user/bids`. Body-selection order in the client:
     - If `bid_id` is present: first attempt with `{ "bid_id": ... }`. On 422/400 and if `flight_id` is also present: second attempt with `{ "flight_id": ... }`.
     - If only `flight_id` is present (`bid_id=None`): direct attempt with `{ "flight_id": ... }` — per the [phpVMS API docs](https://docs.phpvms.net/api/apis), this is a valid body. Some VAs don't provide a bid ID in `PirepSummary`, in which case this is the only path to free the aircraft via bid drop.
     - If both are `None`: step 2 is skipped, only `cancel_pirep` from step 1. This is OK because the aircraft is already freed by `cancel_pirep` — the bid drop is additive, not a mandatory step.
     - Reference: phpVMS source `UserController::bids` accepts both body keys ([api-client/src/lib.rs:1158](client/src-tauri/crates/api-client/src/lib.rs:1158)).
- **Local cleanup** (always, regardless of API result):
  - `discard_queued_positions_for(&app, &pirep_id)` — discard old backlog positions
  - `pirep_queue::remove(&app, &pirep_id)` — if present in the pending_pireps queue
  - **Do NOT** touch the active `state.active_flight` — that is a different flight
- **Activity log:**
  ```
  WARN  Flight GAF 152 manually cancelled
        PIREP xyz cancelled, bid 12345 dropped
  ```
- **Error handling per step:**
  - 404 from `cancel_pirep`: PIREP no longer exists server-side → log success, proceed to bid drop
  - 404 from `delete_bid`: bid already gone → ignore
  - 401/403: → `UiError::new("blocked", "phpVMS rejects — account suspended?")` (B-007 path)
  - Network error: → return a retryable error, pilot can try again later

#### `flight_forget_remote(pirep_id: String) -> Result<(), UiError>`
- Local-only variant for cases where `cancel_pirep` responds with 404 but the pilot is **certain** nothing else is there.
- Performs ONLY the local cleanup, no phpVMS call.
- Activity log: "Flight GAF 152 forgotten locally (no server call)."

    }
  }

## B-012 — Touchdown Airport Field Shows Planned Destination

### Status Quo

In [client/src-tauri/src/lib.rs:12298](client/src-tauri/src/lib.rs:12298) (MQTT TouchdownPayload) and in `build_landing_record`, the `airport` field is hardcoded to `flight.arr_airport.clone()` — i.e. the planned destination code. That's correct for a normal flight but wrong for a crash.

### What We Want

Cascade:
1. **`runway_match.airport_ident`** if the touchdown edge could be unambiguously matched to a runway — authoritative.
2. **Nearest airport within 25 nmi** if there's no runway correlation but the TD position is known — via `runway::find_nearest_airports(lat, lon, 25 * 1852, 1)`.
3. **`flight.arr_airport`** as a last fallback if neither works (total off-airport, no airport within 25 nmi).

### Implementation

Helper function in `lib.rs` — returns a **struct** so the UI/web app can render a banner with source and distances:

```rust
/// Source from which the touchdown-airport resolution came.
/// The frontend uses the value to choose the appropriate hint text.
#[derive(Debug, Clone, Copy, Serialize, Deserialize, PartialEq, Eq)]
#[serde(rename_all = "snake_case")]
pub enum TouchdownAirportSource {
    /// Touchdown edge could be matched to a runway.
    RunwayMatch,
    /// No runway match, but an airport within 25 nmi.
    /// `nearest_distance_nm` is set.
    Nearest25Nm,
    /// Total off-airport — fallback to the planned destination.
    /// `nearest_distance_nm` is None.
    PlannedFallback,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TouchdownAirportResolution {
    /// ICAO of the resolved landing (or fallback destination).
    pub icao: String,
    /// Which cascade step applied.
    pub source: TouchdownAirportSource,
    /// How far away from the planned `flight.arr_airport`. If the
    /// resolution airport == planned, this is 0.0. If None: the planned
    /// coordinates were not in the local airport cache.
    pub distance_to_destination_nm: Option<f32>,
    /// For `Nearest25Nm`: distance from the TD position to the found
    /// nearest airport, in nmi. For other sources: None.
    pub nearest_distance_nm: Option<f32>,
}

fn resolve_touchdown_airport(
    runway_match: Option<&runway::RunwayMatch>,
    landing_lat: Option<f64>,
    landing_lon: Option<f64>,
    planned_arr_airport: &str,
    airport_lookup: impl Fn(&str) -> Option<(f64, f64)>,  // see note below
) -> TouchdownAirportResolution {
    let planned_coords = airport_lookup(planned_arr_airport);
    let dist_to_planned = |lat: f64, lon: f64| -> Option<f32> {
        planned_coords.map(|(plat, plon)| {
            (geo::distance_m(lat, lon, plat, plon) / 1852.0) as f32
        })
    };

    if let Some(rw) = runway_match {
        let dist = match (landing_lat, landing_lon) {
            (Some(la), Some(lo)) => dist_to_planned(la, lo),
            _ => None,
        };
        return TouchdownAirportResolution {
            icao: rw.airport_ident.clone(),
            source: TouchdownAirportSource::RunwayMatch,
            distance_to_destination_nm: dist,
            nearest_distance_nm: None,
        };
    }
    if let (Some(lat), Some(lon)) = (landing_lat, landing_lon) {
        const TD_NEAREST_RADIUS_NM: f64 = 25.0;
        let nearest = runway::find_nearest_airports(
            lat, lon, TD_NEAREST_RADIUS_NM * 1852.0, 1,
        );
        if let Some(closest) = nearest.first() {
            return TouchdownAirportResolution {
                icao: closest.icao.clone(),
                source: TouchdownAirportSource::Nearest25Nm,
                distance_to_destination_nm: dist_to_planned(lat, lon),
                nearest_distance_nm: Some((closest.distance_m / 1852.0) as f32),
            };
        }
        // Position known, but no airport in range → fallback
        return TouchdownAirportResolution {
            icao: planned_arr_airport.to_string(),
            source: TouchdownAirportSource::PlannedFallback,
            distance_to_destination_nm: dist_to_planned(lat, lon),
            nearest_distance_nm: None,
        };
    }
    TouchdownAirportResolution {
        icao: planned_arr_airport.to_string(),
        source: TouchdownAirportSource::PlannedFallback,
        distance_to_destination_nm: None,
        nearest_distance_nm: None,
    }
}
```

**Note on the `airport_lookup` parameter:** The spec does not prescribe a concrete type. The implementer chooses the appropriate path from the existing code — likely candidates:
- `AppState::airports` (HashMap cache, populated from bid pickup) — as a closure `|icao| airports.get(icao).map(|a| (a.lat, a.lon))`.
- A direct `runway::find_nearest_airports(lat=?, lon=?, ...)` reverse path doesn't work because we need the coordinates of the planned airport, not "nearest to lat/lon".
- If no cache hits: API round trip `client.get_airport(icao)` as a fallback — but this shouldn't be necessary in a normal flight workflow, because the bid pickup already preloads the airport.

Important: the resolution function stays **synchronous** (no `.await`). If the concrete lookup path had to be async, this can be solved via pre-fetch + closure capture.

**Two call sites** need to be updated — both use the `icao` field of the resolution for the existing `airport: String` fields in the payload/record:
- MQTT `TouchdownPayload.airport` (lib.rs ~12298). Plus append new optional fields `airport_source`, `airport_distance_to_destination_nm`, `airport_nearest_distance_nm` to `TouchdownPayload` so the web app can render the banner.
- `build_landing_record` LandingRecord construction (lib.rs ~8385). Plus the same fields on the `LandingRecord` struct.

### UI Consequence

**Pilot client LandingPanel and web app LandingAnalysis** continue to show `airport` as the main value. An additional banner is rendered when `source != RunwayMatch` OR `source == RunwayMatch && icao != flight.arr_airport`:

> ⚠ **Off-airport touchdown**
> Planned destination: **EDDB**
> Actual touchdown at: **UMKK** *(nearest, 24.3 nmi from the TD point)*
> Distance to planned destination: **540 nmi**

For `source == PlannedFallback` with lat/lon:

> ⚠ **Off-airport touchdown with no nearby airport**
> Planned destination: **EDDB**
> Touchdown position: 54.83°N / 20.15°E *(540 nmi from plan)*
> No airport within 25 nmi of the TD position.

Web app mirror in `LandingAnalysis.tsx` — both sides consistent, same wording.

### Edge Cases

- **Sea crash** (GAF 152): lat/lon is 30 km before UMKK → `Nearest25Nm` with `nearest_distance_nm ≈ 16 nmi`, banner shows UMKK as nearest and a 540-nmi distance to the planned EDDB.
- **Sea crash with nothing in range** (pilot crashes in the middle of the Atlantic): `PlannedFallback` with lat/lon set → special banner without nearest.
- **Diversion**: pilot lands at the alternate. `runway_match` applies with the alternate ICAO. `distance_to_destination_nm` ≠ 0 → banner shows that the landing wasn't at the planned destination.
- **Multi-runway airport**: `runway_match.airport_ident` is unambiguous, no conflict.

## B-013 — Sim Position Reset Detection

### Status Quo

The touchdown sampler in `spawn_touchdown_sampler` ([lib.rs:10894](client/src-tauri/src/lib.rs:10894)) takes EVERY SimSnapshot sample and pushes it into the buffer. In the GAF-152 incident, MSFS produced a sample with `alt=53,820 ft, lat=0.007, lon=0.000` — the sampler accepted it and 1 second later logged a 14-G crash in the Baltic Sea from it.

### What We Want

**Three detection criteria** before the buffer push, a single match is enough to discard:

1. **Null Island**: `lat.abs() < 0.1 && lon.abs() < 0.1` → classic MSFS position-reset artifact (Gulf of Guinea, 0°/0°). Real flights never happen there.
2. **Altitude jump**: `|snap.altitude_msl_ft - prev_snap.altitude_msl_ft| > 10,000 ft` since the last sample (~20 ms) → physically impossible. Not even an F-16 in a vertical climb manages that.
3. **Position jump**: `haversine(prev_lat/lon, snap.lat/lon) > 10 nmi` in 20 ms → teleport. Corresponds to >1,800 kt true ground speed, doesn't exist.

### On a Match

- **Discard the sample** — no push into the `snapshot_buffer`, no edge detection, no update of `prev_in_air`.
- **Do NOT update `prev_sample_for_reset_check`** — otherwise "the detector gets used to the reset" and the next real sample jumps >10 nmi away from 0/0 again.
- **Activity log** (rate-limited, once per sampler session):
  ```
  WARN  Sim position reset detected — sample discarded
        lat=0.007, lon=0.000, alt=53820 ft, jump_nm=12450
        Reason: lat/lon ≈ 0/0 (Null Island)
  ```

### Implementation

In the sampler loop directly after `current_snapshot(&app)` and BEFORE `stats.snapshot_buffer.push_back(...)`:

```rust
// Stores (lat, lon, alt_msl_ft, sampled_at) — we need dt
// to detect stale prev_state after pause/disconnect.
let mut prev_sample_for_reset_check: Option<(f64, f64, f64, DateTime<Utc>)> = None;
let mut reset_warning_logged_this_session = false;
const RESET_NULL_ISLAND_DEG: f64 = 0.1;
const RESET_MAX_ALT_JUMP_FT: f64 = 10_000.0;
const RESET_MAX_DIST_NM_PER_TICK: f64 = 10.0;
// Maximum time span between two samples within which the jump checks
// are still meaningful. Over a longer gap (pause, disconnect, app
// backgrounded), large legitimate jumps are expected, so we skip
// the sample check and simply reset prev_state instead.
const RESET_CHECK_MAX_DT_SECS: i64 = 2;

// ... loop start, snap = current_snapshot, now = Utc::now() ...

let is_null_island = snap.lat.abs() < RESET_NULL_ISLAND_DEG
    && snap.lon.abs() < RESET_NULL_ISLAND_DEG;

// dt guard: jump checks only for closely-spaced samples.
// With too large a gap since prev_state, a jump is expected
// (reposition after pause, resume from disconnect) — in that case we
// just reset prev_state and only look again at the next close sample pair.
let (alt_jump, dist_jump_nm, dt_too_large) = match prev_sample_for_reset_check {
    Some((p_lat, p_lon, p_alt, p_at)) => {
        let dt = (now - p_at).num_seconds();
        if dt > RESET_CHECK_MAX_DT_SECS {
            // Too long ago — skip jump check, prev_state is
            // reset below with the current sample.
            (0.0, 0.0, true)
        } else {
            let dist_m = geo::distance_m(p_lat, p_lon, snap.lat, snap.lon);
            let dist_nm = dist_m / 1852.0;
            let alt_diff = (snap.altitude_msl_ft - p_alt).abs();
            (alt_diff, dist_nm, false)
        }
    }
    None => (0.0, 0.0, false),
};

let is_alt_jump = !dt_too_large && alt_jump > RESET_MAX_ALT_JUMP_FT;
let is_dist_jump = !dt_too_large && dist_jump_nm > RESET_MAX_DIST_NM_PER_TICK;

if is_null_island || is_alt_jump || is_dist_jump {
    if !reset_warning_logged_this_session {
        let reason = if is_null_island {
            "lat/lon ≈ 0/0 (Null Island)"
        } else if is_alt_jump {
            "Altitude jump > 10,000 ft"
        } else {
            "Position jump > 10 nmi"
        };
        tracing::warn!(
            pirep_id = %flight.pirep_id,
            lat = snap.lat, lon = snap.lon, alt_ft = snap.altitude_msl_ft,
            alt_jump_ft = alt_jump, dist_jump_nm = dist_jump_nm,
            reason = reason,
            "Sim position reset detected — sample discarded"
        );
        reset_warning_logged_this_session = true;
    }
    continue;  // skip buffer push + edge detect, prev_state stays
               // deliberately unchanged so no phantom edge is
               // triggered after the reset.
}

// Sample is OK OR dt was too large (resume case) — reset prev_state.
prev_sample_for_reset_check = Some((snap.lat, snap.lon, snap.altitude_msl_ft, now));

// ... existing buffer push code ...
```

- Normal sample → passes through, prev_state updated
- Brutal altitude jump (5,000 → 50,000 ft in one tick) → discarded

## B-014 — Auto-File Attempt Before Session End for a Finalizable Flight

### Status Quo — What We Had to Correct

**The assumption about GAF 152 was wrong:** In the JSONL dump, session 717 and session 718 had an identical timestamp `1778615953905` — from this we had concluded that F7 performs an automatic aircraft-switch session reset. **The code truth is different:**

- The v0.7.15 F7 detector lives in [`apply_pause_resume`](client/src-tauri/src/lib.rs:10452) and does **only an activity-log warning** ("⚠ Aircraft mismatch after resume: sim reports X, bid expects Y"). No session reset whatsoever.
- [`flight_start`](client/src-tauri/src/lib.rs:4273) strictly refuses when `active_flight.is_some()` — no implicit replace.
- There is **no automatic** path in the code that ends an active session on an aircraft change.

→ In the GAF-152 case, the **pilot manually** ended session 717 (via `flight_cancel` or the `flight_forget` button) before reopening session 718 via `flight_start`. The identical backend timestamp is a coincidence of the cancel→start sequence happening within the same second.

### What We Actually Need to Prevent

The **real risk**: when the pilot cancels a flight via `flight_cancel` that would actually still be filable (in LANDING / TaxiIn / BLOCKS_ON / Arrived with a valid TD), the PIREP opportunity is lost. Currently ([lib.rs:9989](client/src-tauri/src/lib.rs:9989)), `flight_cancel` calls `cancel_pirep` directly — no file attempt first.

### What We Want

**Refactor `flight_cancel` to "file-first, cancel-second" with a three-part `AutoFileOutcome`:**

```rust
/// Result of the `attempt_auto_file` helper. Caller decides what happens
/// based on the variant. Important: `Queued` is NOT a cancel trigger —
/// the PIREP is already in pirep_queue for a later retry, cancelling it
/// would be data loss.
pub enum AutoFileOutcome {
    /// PIREP was successfully sent to phpVMS, status PENDING.
    /// active_flight has already been cleared.
    Filed { pirep_id: String },
    /// Transient error (network, 5xx, timeout). PIREP was placed in
    /// pirep_queue for background retry, active_flight has been cleared.
    /// The pilot can start the next flight; the worker submits the
    /// PIREP as soon as the connection is back.
    Queued { pirep_id: String, retry_after_secs: u32 },
    /// Hard failure (validation, 4xx other than 401/403, missing fields).
    /// Retry is NOT sensible. active_flight is UNCHANGED
    /// (= the flight stays active so the pilot can correct or
    /// explicitly cancel if needed).
    HardFailed { reason: String, code: String },
}

#[tauri::command]
async fn flight_cancel(
    app: AppHandle,
    state: tauri::State<'_, AppState>,
    force: Option<bool>,   // UI "discard anyway" button → true
) -> Result<FlightCancelOutcome, UiError> {
    // STEP 1 — READ only, so we can determine is_finalizable.
    // We only do `guard.take()` further down at the actual cleanup,
    // otherwise the flight would be gone on an interim error without
    // anything having happened.
    let (flight, is_finalizable) = {
        let guard = state.active_flight.lock().expect("active_flight lock");
        let flight = guard
            .as_ref()
            .cloned()
            .ok_or_else(|| UiError::new("no_active_flight", "no flight is active"))?;
        let is_finalizable = {
            let stats = flight.stats.lock().expect("flight stats");
            // Assumption: as long as the flight sits in state.active_flight AND
            // a valid `landing_at` marker is set AND the FSM phase is a
            // TD phase, the flight hasn't been filed yet (filed flights
            // clean up `state.active_flight` themselves via the `flight_end` path).
            matches!(
                stats.phase,
                FlightPhase::Landing
                | FlightPhase::TaxiIn
                | FlightPhase::BlocksOn
                | FlightPhase::Arrived
            ) && stats.landing_at.is_some()
        };
        (flight, is_finalizable)
    };

    let user_forced_cancel = force.unwrap_or(false);

    if is_finalizable && !user_forced_cancel {
        // Best-effort: try to file first.
        // attempt_auto_file gets &state so, on success/queue, it can
        // clear the active_flight slot itself (analogous to the flight_end path).
        match attempt_auto_file(&app, &state, &flight).await {
            AutoFileOutcome::Filed { pirep_id } => {
                log_activity(&state, ActivityLevel::Info,
                    format!("Flight {} {} → {} filed properly instead of cancelled",
                        format_callsign(...), flight.dpt_airport, flight.arr_airport),
                    Some(format!("PIREP {}", pirep_id)));
                // active_flight was cleared by attempt_auto_file.
                return Ok(FlightCancelOutcome::FiledInstead { pirep_id });
            }
            AutoFileOutcome::Queued { pirep_id, .. } => {
                // CRITICAL: do NOT fall into the cancel path. The PIREP is
                // in the queue and will be submitted automatically once
                // the connection is back. Cancelling would pull the queue
                // entry out from under the worker → data loss.
                log_activity(&state, ActivityLevel::Warn,
                    format!("Auto-file failed transiently — PIREP {} sits in the queue for later retry",
                        pirep_id),
                    Some("The next flight can be started — the worker will submit the PIREP automatically.".into()));
                // active_flight was cleared by attempt_auto_file.
                return Ok(FlightCancelOutcome::Queued { pirep_id });
            }
            AutoFileOutcome::HardFailed { reason, code } => {
                // SPECIAL CASE: 401/403 account suspension / API key revoked.
                // `cancel_pirep` would also return 401/403 → no sensible
                // cancel path. `state.active_flight` deliberately stays
                // in place so the pilot can retry the cancel later after
                // clarifying with the VA admin (or clean up via the
                // B-011 orphan cleanup once the account is unblocked).
                if code == "blocked" {
                    log_activity(&state, ActivityLevel::Error,
                        "phpVMS is rejecting your requests — account suspended or inactive",
                        Some(format!("{reason} — contact VA admin, then try cancel again.")));
                    return Err(UiError::new("blocked", reason));
                }

                // Other hard failures (validation 4xx, BadResponse,
                // not_at_arrival, etc.): file attempt is pointless. Falls
                // through to the cancel path. `state.active_flight` is
                // still SET here (HardFailed doesn't clear it), which the
                // cancel path below does via `guard.take()`.
                log_activity(&state, ActivityLevel::Warn,
                    format!("Auto-file before cancel failed ({code}) — PIREP is now being cancelled"),
                    Some(format!("{reason}")));
                // Fall through to the cancel path below.
            }
        }
    }

    // STEP 2 — Cancel path. Only NOW take the flight out of
    // state.active_flight (`guard.take()`), before doing anything
    // destructive. If a second UI action tried to do a flight_start
    // in the meantime, it would fail with `flight_already_active` —
    // that is intentional.
    let flight = {
        let mut guard = state.active_flight.lock().expect("active_flight lock");
        // Safety check: can the caller (HardFailed/forced) still find
        // the SAME flight here? Should be — no one else clears
        // active_flight between step 1 and step 2 in the same task.
        guard
            .take()
            .ok_or_else(|| UiError::new("no_active_flight",
                "flight was concurrently removed — likely already filed"))?
    };

    // Original cancel_pirep path — see lib.rs:9989.
    flight.position_outbox.lock().expect("position_outbox lock").clear();
    flight.stop.store(true, Ordering::Relaxed);
    let client = current_client(&state)?;
    let result = client.cancel_pirep(&flight.pirep_id).await;
    clear_persisted_flight(&app);
    discard_queued_positions_for(&app, &flight.pirep_id);
    pirep_queue::remove(&app, &flight.pirep_id);
    result?;
    log_activity(&state, ActivityLevel::Warn,
        format!("Flight cancelled: {} {} → {}", ...),
        Some(format!("PIREP {}", flight.pirep_id)));
    record_event(&app, &flight.pirep_id, &FlightLogEvent::FlightEnded { ... });
    Ok(FlightCancelOutcome::Cancelled)
}
```

**New helper** `attempt_auto_file(app: &AppHandle, state: &tauri::State<AppState>, flight: &Arc<ActiveFlight>) -> AutoFileOutcome`:
- Signature deliberately takes `&state` — the helper clears the `state.active_flight` slot itself on `Filed` and `Queued`, exactly analogous to the existing `flight_end` path ([lib.rs ~9555+](client/src-tauri/src/lib.rs:9555)). On `HardFailed`, `active_flight` stays unchanged; the caller decides what happens.
- Extracts the PIREP-filing logic from the existing `flight_end` path. Same validation (see [pirep-filing-validation-policy.md](pirep-filing-validation-policy.md)), same backlog-drain strategy.
- Mapping of API result → `AutoFileOutcome`:
  - HTTP 2xx → `Filed`. **The helper clears `state.active_flight`** via `guard.take()` AND `clear_persisted_flight(app)` AND `discard_queued_positions_for(app, pirep_id)`.
  - `ApiError::Network` / `ApiError::Server { status: 500..=599 }` / timeout (= `is_transient_pirep_error()`) → `pirep_queue::enqueue` + `Queued`. **The helper clears `state.active_flight`** same as for `Filed` — so the pilot can start the next flight while the worker submits the PIREP in the background.
  - `ApiError::Server { status: 4xx }` other than 401/403 / `ApiError::BadResponse` / validation error → `HardFailed`. **The helper clears NOTHING** — `state.active_flight`, `position_outbox`, and the persisted flight remain unchanged. The caller (`flight_cancel`) decides (continue the cancel path) or shows an error.
  - `ApiError::Unauthenticated` / `ApiError::Forbidden` (B-007 account suspension) → `HardFailed` with code `"blocked"`. The caller can show the pilot a dedicated message instead of a cancel.

**Side-effect contract (for tests + reviews):**

| Outcome | Does the helper clean up `state.active_flight`? | `pirep_queue` |
|---|---|---|
| `Filed` | ✅ yes, via `guard.take()` | not touched |
| `Queued` | ✅ yes | entry via `pirep_queue::enqueue` |
| `HardFailed` | ❌ no — caller's responsibility | not touched |

**Frontend outcome type** in `types.ts`:

```typescript
export type FlightCancelOutcome =
  | { kind: "filed_instead"; pirep_id: string }
  | { kind: "queued"; pirep_id: string }
  | { kind: "cancelled" };
```

The UI renders a different confirmation per outcome:
- `FiledInstead`: ✅ "Flight filed properly instead of discarded — PIREP `{id}`"
- `Queued`: ⏳ "PIREP is waiting in the queue — will be submitted automatically once the connection is back"
- `Cancelled`: ⚠ "Flight cancelled, PIREP `{id}` marked as CANCELLED"

**UI consequence:** The confirm dialog before `flight_cancel` is extended when `is_finalizable`:
> ⚠ **Really cancel the flight?**
>
> Your flight is actually almost done (LANDING/TaxiIn). Cancelling would discard the PIREP.
>
> [ Try to file instead ]   [ Cancel ]   [ Discard anyway ]

### Rationale — Outcome per Case

The three `AutoFileOutcome` variants are handled deliberately differently. Above all: **Queued is NOT a cancel trigger.**

| Case | `AutoFileOutcome` | What happens | Data-loss risk |
|---|---|---|---|
| File succeeds cleanly | `Filed` | PIREP filed, `state.active_flight` cleared, UI shows "filed instead of discarded" | None — best outcome |
| Network down / 5xx / timeout (transient) | `Queued` | PIREP in `pirep_queue::enqueue` for worker retry, `state.active_flight` cleared, UI shows "waiting in the queue". **Cancel is NOT executed** | None — worker submits once network is back. **Cancel would pull the queue entry out from under it!** |
| Validation / 4xx (except 401/403) | `HardFailed { code, reason }` | No retry sensible. `state.active_flight` STAYS. Caller (`flight_cancel`) continues with the cancel path: `guard.take()` + `cancel_pirep` + local cleanup. Activity log shows why the file failed | PIREP is lost — intentional, the pilot confirms beforehand in the 3-button confirm |
| 401/403 (account suspension B-007) | `HardFailed { code: "blocked" }` | No cancel attempt — `cancel_pirep` would also throw 401/403. UI shows the B-007 banner instead of cancel | None — pilot has to contact the VA admin |
| No TD happened (cancel mid-cruise) | (no `attempt_auto_file` call) | `is_finalizable=false` → direct cancel path as before v0.7.18 | Expected state |
| Pilot clicks "discard anyway" | (no `attempt_auto_file` call) | `force=true` → direct cancel path. Pilot has explicitly chosen | Pilot decision, intentional |

**Clear rule for the implementation:** the only path in which `flight_cancel` falls into the actual cancel code after a file attempt is **`HardFailed` with `code != "blocked"`**. `Filed`, `Queued`, and `HardFailed{code:"blocked"}` return immediately, without touching the cancel path. On `blocked`, a `UiError("blocked", …)` is returned so the frontend shows a B-007-consistent suspension banner instead of suggesting a cancel.

### Edge Cases

- **Pilot changes aircraft mid-cruise** (before touchdown): F7 warns in the activity log (unchanged). If the pilot manually clicks cancel, `is_finalizable=false` → cancel immediately, no file attempt.
- **Pilot changes aircraft after BLOCKS_ON** (seat swap on the ground): F7 warns. If the pilot then clicks cancel: `is_finalizable=true` → the file attempt most likely succeeds → the PIREP is filed cleanly instead of discarded.
- **Pilot absolutely wants to cancel despite being filable** (e.g. because it's unclear how a crash should be filed): "discard anyway" button in the extended confirm dialog → direct cancel path without a file attempt.

## Across All Four: API Operations Inventory

### `cancel_pirep(pirep_id)` — phpVMS Server Cancel

- **phpVMS standard route:** `DELETE /api/pireps/{pirep_id}/cancel`
- **phpVMS fallback route:** `PUT /api/pireps/{pirep_id}/cancel`
- **Current client state:** [api-client/src/lib.rs:1344](client/src-tauri/crates/api-client/src/lib.rs:1344) still uses `POST /api/pireps/{pirep_id}/cancel` and needs to be corrected to `DELETE` plus `PUT` fallback for v0.7.18.
- **Server-side effect:** PIREP state 0 (IN_PROGRESS) → 3 (CANCELLED), status → CANCELLED. phpVMS fires a `PirepCancelled` event. Aircraft release is the expected phpVMS/VA behavior and must be verified in QA against live.kant.ovh.
- **Non-pilot view:** PIREP remains visible in the VA PIREP list (CANCELLED filter), but not in pilot stats.
- **Used in B-011 + B-014.**

### `delete_bid(bid_id, flight_id?)` — Drop a Bid

- **phpVMS standard route:** `DELETE /api/user/bids` (no `{id}` in the path — bid_id travels in the body).
- **Preferred body:** `{ "bid_id": 123 }` — accepted by the phpVMS source (`UserController::bids`).
- **Fallback body:** `{ "flight_id": "flightid_1" }` — as described in the official phpVMS docs. Some VA configurations only accept this variant.
- **Current client state:** [api-client/src/lib.rs:1150](client/src-tauri/crates/api-client/src/lib.rs:1150) uses `DELETE /api/user/bids` with `{ bid_id }`. **No `flight_id` fallback implemented**, **no 405 fallback** (contrary to the function comment — the code only makes the DELETE attempt).
- **Server-side effect:** the bid is deleted. Some VA configs bind the aircraft to the bid instead of the PIREP — in that case the bid must go for the aircraft to be freed.
- **Extension for B-011:**
  - If the DELETE with `{ bid_id }` responds with `422`/`400`/`404` AND `flight_id` is known from the `OrphanFlight`: make a second attempt with `{ flight_id }`.
  - The 405 fallback (POST with `_method=DELETE`) stays out of scope — if a VA setup genuinely needs it, better to add it as a separate task after v0.7.18 rather than building it in blindly now.
- **Used in B-011 (optional, depending on `bid_id.is_some()` OR `flight_id.is_some()` — see the `flight_cancel_orphan` logic above. If both are None: step 2 is skipped, only `cancel_pirep` runs.**

### Local Forget — `discard_queued_positions_for` + `pirep_queue::remove`

- **`discard_queued_positions_for`** already exists (see [lib.rs:5730](client/src-tauri/src/lib.rs:5730)).
- **`pirep_queue::remove(&app, &pirep_id)`** already exists and cleans up the pending_pireps retry worker.
- **No API calls**, pure filesystem operations.

### What Does NOT Exist — and Why

- **`delete_pirep_entirely`** — phpVMS has no API endpoint to delete a PIREP entirely from the database. `cancel_pirep` is the closest approximation: the PIREP remains visible in the DB (for VA audit) but no longer counts as filed.
- **`release_aircraft_directly`** — doesn't exist. phpVMS manages aircraft availability internally based on PIREP states. When a stuck PIREP is cancelled, the aircraft is automatically freed.

### Disposable Basic / Fix Aircraft State — Check the Logic, Don't Use as an Admin Fallback

Disposable Basic offers a tool called **Fix Aircraft State / Park Aircraft** in the phpVMS admin. Screenshot note: if the aircraft has an active `IN_PROGRESS` PIREP, that PIREP is also set to `CANCELLED` there.

**This is interesting for AeroACARS as a logic template, but not as a UI fallback.**

- Does the installed Disposable Basic code have a controller/service for `Fix Aircraft State` that does more than:
  1. Look up the aircraft by registration,
  2. cancel this aircraft's active `IN_PROGRESS` PIREPs,
  3. set the aircraft state to `PARKED`?
- Does the Disposable logic fire the same phpVMS events as `PirepService::cancel()` (`PirepCancelled`), or does it write directly to DB columns?
- Is the bid also deleted, or only the PIREP/aircraft state corrected?
- Which phpVMS version/Disposable Basic version is running on `live.kant.ovh`?

**Security boundary:**
- No pilot API may cancel purely by aircraft registration. Otherwise pilot A with `D-AIAI` could accidentally or intentionally end pilot B's active flight.
- AeroACARS may only cancel PIREPs that belong to the current API key/pilot via `GET /api/user/pireps?state=0`.
- A server-side admin repair function would only be acceptable if it additionally checks: `pirep.user_id == current pilot`, `pirep.state == IN_PROGRESS`, optionally `pirep.source == ACARS/AeroACARS`.

**Preliminary conclusion:**
- For B-011, the safe standard path remains: PIREP-ID-based `DELETE /api/pireps/{id}/cancel`, then bid drop and local cleanup.
- Disposable Basic is included as a **research source**. If the code confirms that a necessary aircraft-state repair happens there, we'll define from it either:
  - a small phpVMS add-on endpoint for AeroACARS with a pilot-ownership check, or
  - a recorder/admin repair route for VA admins, but not as a blind registration button in the pilot client.

### Repositioning the Aircraft to a Different Airport

phpVMS resets the aircraft on cancel to the **departure airport of the cancelled PIREP** (or the last logged position, depending on VA plugin config). For GAF 152: it would park again in UMKK (where the flight started).

**What we cannot control from the client:** placing it at a *different* airport (e.g. the pilot accidentally booked UMKK instead of LEAL and wants the aircraft to now be in LEAL). That's a VA admin action in the phpVMS web UI.

→ **Communicate explicitly in the confirm dialog:** "The aircraft will be freed and parked at the departure airport. If it needs to be elsewhere, ask the VA admin."
